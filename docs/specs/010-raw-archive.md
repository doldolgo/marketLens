# 010 — raw-archive

상태: DONE | 의존: 001(collect — 원문 싱크 계약·거래소별 수신 경로), 006(wallet-status — REST 응답 원문), 007(deploy — env 주입·EC2 IAM 역할), 012(binance-stream — 바이낸스 수신 경로)

> 이 문서는 이 기능이 **지금 어떻게 동작해야 하는지**를 적는다. 동작이 바뀌면 이 문서를 직접 고치고, 같은 PR 에서 코드·테스트도 맞춘다(CLAUDE.md §4·§6). 사람이 끝까지 읽는 문서다 — 코드를 산문으로 옮기지 않는다.
> 구현 구조(클래스·함수·파일 내부)는 실행 세션의 몫이다. 여기엔 **무엇이 어떻게 동작해야 하는가**만 쓴다.

## 1. 목적
거래소에서 서버로 들어오는 **모든 응답을 받은 그대로** S3 에 남긴다. WebSocket 메시지 한 건, REST 응답 한 건이 각각 한 줄이고, 줄에는 원문 외에 "어느 거래소에서, 어느 경로로, 언제 받았는가" 세 가지만 덧붙는다.
이 아카이브가 있으면 나중에 쓰는 필드·계산식·저장 모양이 바뀌어도 **처음부터 다시 수집할 필요 없이** 원문을 다시 읽어 재생할 수 있다. 가공된 값(김프·행 표)은 여기 남기지 않는다 — 가공값은 InfluxDB(005·009)의 몫이고, 이 저장소의 존재 이유는 가공 전 원문 보존이다.

## 2. 범위
- 만드는 것: 공유 인프라의 **원문 싱크**(수신 경로가 호출하는 기록 함수 — 거래소별 버퍼·객체 조립·닫기 회차·업로드 워커), S3 업로더(연결·쓰기), env `S3_BUCKET`·`S3_REGION`, 테스트.
- 하지 않는 것: 원문을 읽는 HTTP 엔드포인트(사람이 S3 콘솔·CLI·pandas 로 본다). 재생(replay) 도구 — 재생이 **가능하도록 줄 모양을 고정**하는 것까지가 이 스펙이다(§3.7). 보존기간·lifecycle(버킷 설정은 사람 몫, 코드는 관여하지 않는다). 소급 업로드. FE 표시. 가공된 표·김프의 S3 저장 — 하지 않는다.
- 바꾸는 기존 것: 배포 워크플로(`.github/workflows/deploy.yml`)의 env 가드(`server/.env` 의 `S3_BUCKET` 이 비어 있으면 배포 중단)는 그대로. `docs/runbooks/ec2-setup.md` 의 IAM 정책 접두사를 `raw/*` 로.

## 3. 동작

### 3.1 읽는 계약 (복사)
- 001·012: 거래소 수신 경로는 **WebSocket 상시 연결**(업비트·빗썸 `wss://…/websocket/v1`, 바이낸스 `wss://data-stream.binance.vision/stream`)과 **REST 호출**(마켓 목록 `/v1/market/all`, 바이낸스 `/api/v3/exchangeInfo`, 006 의 입출금 상태 3종)이다. 수신 경로는 페이로드를 **해석하기 전에** 원문 싱크의 기록 함수를 부른다. 프레임이 바이너리면 UTF-8 로 디코드한 문자열, 압축(permessage-deflate)이면 라이브러리가 푼 뒤의 문자열이 원문이다.
- 001: 원문 싱크의 계약은 core 공개 함수 하나 — `record(exchange: str, source: str, received_at_ms: int, payload: str) -> None`. **동기이며 예외를 던지지 않는다**(수신 경로를 한 줄도 막지 않기 위해). `source` 는 `"ws:<경로>"` 또는 `"rest:<경로>"`(예 `ws:/websocket/v1`, `rest:/v1/market/all`, `rest:/sapi/v1/capital/config/getall`). `received_at_ms` 는 서버가 받은 시각(epoch ms).
- 006(006 구현 시): 입출금 상태 REST 응답 본문(성공·실패 모두)도 같은 함수로 기록된다. 키·서명·토큰은 **요청** 쪽에만 있고 응답 본문에는 없다. 006 이 `record` 를 주입하기 전까지 입출금 REST 응답은 아카이브에 없다.
- 배포 워크플로(`.github/workflows/deploy.yml` — 007 스펙 본문에는 이 가드가 없다): `server/.env` 의 `S3_BUCKET` 이 비어 있으면 배포를 중단한다. 앱의 켜는 조건은 `S3_BUCKET` 존재(§3.2). 자격증명은 SDK 기본 탐색(로컬 `~/.aws`, EC2 는 IAM 역할 — `docs/runbooks/ec2-setup.md`).

### 3.2 설정·인증
- env 두 개(`server/.env`, 사람이 채운다): `S3_BUCKET` — 없거나 비어 있으면 **아카이브 비활성**(기록 함수는 아무것도 하지 않고, 앱은 뜬다, 경고 로그 1줄). `S3_REGION` — 기본 `ap-northeast-2`. 비어 있으면(`S3_REGION=`) 기본값으로 본다.
- S3 클라이언트를 만드는 것 자체가 실패하면(잘못된 리전 문자열 등) 에러 로그 1줄 + **아카이브 비활성**이고 앱은 뜬다 — 원문 아카이브의 어떤 실패도 기동을 막지 않는다.
- **AWS 액세스 키는 어디에도 적지 않는다.** `.env`·compose·코드에 `AWS_ACCESS_KEY_ID` 류가 등장하면 안 된다.
- 버킷 `marketlens-spreads-snapshot`(ap-northeast-2, 퍼블릭 차단, 버전 관리 끔). 이 스펙은 접두사 **`raw/`** 아래에만 쓴다.

### 3.3 외부 의존 — S3
- 호출은 `PutObject` 뿐(기동 시 `HeadBucket` 1회). 요청당 타임아웃 연결 3초·읽기 30초(객체가 수십 MB 다), SDK 재시도 2회.
- EC2 IAM 역할 최소 권한: 버킷 `raw/*` 접두사에 `s3:PutObject`, 버킷에 `s3:ListBucket`(HeadBucket 용).
- 컨테이너에서 IAM 역할을 쓰려면 인스턴스 메타데이터 hop limit 이 2 여야 한다(docker 브리지 안에서 기본 1 은 닿지 않는다) — 사람의 인프라 작업, ec2-setup 런북.
- 기동 시 `HeadBucket` 실패는 에러 로그 **정확히 1줄**(버킷 이름·원인 포함)이고 앱은 뜬다. 업로드 워커가 객체마다 다시 시도한다(§3.6).

### 3.4 레코드 — 한 줄의 모양
원문 하나 = JSON Lines 한 줄. 키 순서 고정, 구분자 없이 압축(`separators=(",", ":")`).
```json
{"exchange":"upbit","source":"ws:/websocket/v1","receivedAt":1788600000123,"raw":{"type":"orderbook","code":"KRW-BTC","orderbook_units":[{"ask_price":1.0,"bid_price":0.9,"ask_size":1.0,"bid_size":2.0}],"timestamp":1788600000100,"stream_type":"REALTIME"}}
```
- `exchange` — `upbit`·`bithumb`·`binance`. `source` — §3.1 의 문자열. `receivedAt` — 서버 수신 시각(epoch ms).
- `raw` — 페이로드 **원문 그대로**. 페이로드가 유효한 JSON 텍스트면 그 바이트를 줄 안에 **그대로 이어 붙인다**(파싱→재직렬화 금지 — 공백·숫자 표기가 바뀌면 원문이 아니다). 유효한 JSON 이 아니면(HTML 오류 페이지 등) JSON 문자열로 감싼다. 읽는 쪽은 `raw` 의 타입(객체·배열 vs 문자열)으로 둘을 구분한다.
- 그대로 이어 붙이는 조건은 셋 다 만족할 때다: ① 유효한 JSON 텍스트 ② 최상위 값이 객체 또는 배열 ③ 줄바꿈 문자(`\n`·`\r`)가 없음. 하나라도 어긋나면(HTML 오류 페이지, 숫자·문자열 같은 스칼라 JSON, 줄바꿈이 든 pretty-printed JSON, 빈 문자열) JSON 문자열로 감싼다 — 줄바꿈은 문자열 이스케이프로 보존되므로 바이트는 잃지 않고, "한 레코드 = 한 줄" 이 유지된다.
- 줄 안에 가공값·파싱 결과·계산값을 넣지 않는다. 이 세 메타키 외의 키가 생기면 안 된다.

### 3.5 버퍼와 객체
- 거래소마다 버퍼 하나. 기록 함수는 줄을 만들어 그 거래소 버퍼에 붙인다(동기, 메모리만).
- **닫는 조건** 둘 중 먼저 오는 것: ① 60초 경과 ② 버퍼의 비압축 바이트가 32MB 도달. 닫힌 버퍼 = 객체 1개. 두 값은 코드 상수다. "60초 경과" 는 그 버퍼 **첫 줄의 `receivedAt`** 부터 닫기 회차의 현재 시각까지 60,000ms 이상이다. 닫는 주체는 매초 도는 닫기 회차뿐이다 — 기록 함수는 붙이기만 하므로 32MB 는 다음 회차(≤1초 뒤)에 닫힌다. 닫기 회차는 업로드와 독립이라(§3.6) S3 가 느리거나 막혀 있어도 이 주기는 유지된다 — 열린 버퍼는 32MB + 1초치 유입 이상 자라지 않는다.
- 키: `raw/exchange=<id>/dt=YYYY-MM-DD/hh=HH/YYYYMMDDTHHMMSS.mmmZ.jsonl.gz` — 전부 **UTC**, 시각은 그 객체 **첫 줄의 `receivedAt`**. `exchange=`·`dt=`·`hh=` 는 Hive 파티션 관례라 Athena 를 얹을 수 있다. 예: `raw/exchange=binance/dt=2026-09-05/hh=03/20260905T031500.123Z.jsonl.gz`.
- 내용: gzip 압축 JSON Lines, 줄 순서 = 수신 순서. 메타데이터 `Content-Type: application/x-ndjson`, `Content-Encoding: gzip`. 같은 버퍼를 두 번 직렬화하면 바이트까지 같다(gzip mtime 0 고정).
- 빈 버퍼는 객체를 만들지 않는다.
- 크기 감(실측 전 추정): 업비트 KRW 전 마켓 호가·현재가 실시간 + 빗썸 동일 + 바이낸스 300종목 depth20(1초) + 전 종목 미니티커(1초) ≈ 초당 1~2MB 원문 → 하루 원문 90~170GB, gzip 후 **10~20GB/일**. S3 저장비는 GB 당 월 $0.025 수준이라 한 달치가 월 $10 안팎이다. 보존 기간을 정하면 버킷 lifecycle 로 — 코드는 관여하지 않는다. 실측값은 실행 세션이 §5 에 적는다.

### 3.6 닫기 회차와 업로드 워커
- **닫기 회차**: 앱 기동이 관리하는 태스크 하나가 **매 초** 거래소별 버퍼를 보고 §3.5 닫는 조건을 만족한 버퍼를 닫아 gzip 한 뒤 **업로드 대기열** 꼬리에 넣는다. gzip 은 이벤트 루프를 막지 않게 스레드에서 한다. 닫기 회차는 업로드 결과를 기다리지 않는다.
- **업로드 워커**: 대기열을 올리는 주체는 **워커 스레드 하나**뿐이다(동기 SDK). 머리 객체를 `PutObject` 하고 성공하면 뺀 뒤 다음 머리로 간다. 대기열을 만지는 쪽은 닫기 회차(넣기·상한 버림)와 워커(머리 빼기) 둘이며 잠금으로 직렬화한다 — 같은 객체가 두 번 올라가거나, 올리지 않은 객체가 대기열에서 사라지는 일이 없다. 닫기 주기와 업로드가 독립이므로 업로드가 느리거나 실패 중이어도 버퍼는 제때 닫히고, 밀린 양은 대기열(압축 후, 아래 상한)에만 쌓인다.
- 대기열은 거래소를 합쳐 **닫힌 순서 하나의 FIFO** 다 — 거래소마다의 순서는 그 안에서 유지된다. 머리 객체가 실패하면 다른 거래소의 객체도 뒤에서 기다린다(실패 원인은 거의 항상 S3·자격증명 쪽이라 거래소별로 나눠도 이득이 없고, 상한 계산이 하나로 끝난다).
- 실패(자격증명 없음·권한 거부·네트워크·타임아웃): 로그 `S3 원문 업로드 실패 (연속 n회)` 후 그 객체를 대기열 **머리에 그대로 두고** 1초 뒤 다시 시도한다 — 순서가 바뀌지 않는다. 그 사이 다른 객체가 대기열에 들어와도 재시도를 앞당기지 않는다(대기를 끊는 것은 종료뿐). 성공하면 연속 횟수 0.
- 대기열 상한: 거래소 합산 **압축 후 256MB**(코드 상수). 넘치면 가장 오래된 객체부터 버리고 에러 로그에 버린 객체의 키(=시간대)를 남긴다. S3 가 오래 막히면 원문이 유실될 수 있다는 뜻이며, 그 상한이 곧 장애 내성이다. 워커가 올리는 중이던 객체가 버려지면 그 업로드 결과는 대기열에 반영하지 않는다(성공했어도 이미 없는 객체, 실패했어도 다음 머리로).
- 어떤 실패도 수집·`/spreads`·Redis·Influx 경로에 번지지 않는다. 기록 함수는 항상 즉시 돌아온다. 닫기 회차 한 번이 예외로 끝나도(스레드 실행기 종료 등 예상 밖 예외) 예외 로그 1줄 뒤 다음 초의 회차가 돈다 — 회차 태스크는 죽지 않는다.
- 종료: 닫기 회차를 멈추고 열려 있는 버퍼를 전부 닫아 대기열에 넣은 뒤, 워커가 대기열을 비우기를 **합계 5초** 안에서 기다린다. 시간 안에 못 올린 것은 대기열에서 버리고 경고 로그(버린 객체 수)를 남긴다. 워커는 데몬 스레드라 진행 중이던 `PutObject` 가 프로세스 종료를 붙들지 않는다(그 객체는 잃는다) — `docker stop` 의 10초 안에 끝난다. 순서는 스트림이 전부 닫힌 **뒤**(마지막 프레임까지 기록된 뒤)다 — 009 의 인계 큐 비우기(5초 상한)와 직렬이라 Redis·S3 가 동시에 무응답이면 합계가 10초에 닿을 수 있다.
- 기동 시 `S3_BUCKET` 이 있으면 `HeadBucket` 1회로 접근을 확인하고 실패는 에러 로그 1줄이다(§3.3). 자격증명이 없어도 앱은 뜬다 — 그 뒤 실패는 워커의 업로드 실패 로그로만 보인다.

### 3.7 재생 가능성 (이 스펙이 보장하는 성질)
- 줄 하나에서 `exchange`·`source`·`raw` 만으로 001·012 의 해석 규칙(행 조립·USDT 시세 추출)을 **다시 적용할 수 있어야** 한다. 해석에 필요한 정보가 줄 밖(다른 줄·서버 상태)에 있으면 안 된다.
- `receivedAt` 은 서버 시각이다. 거래소 시각은 `raw` 안에 있으므로 두 시계를 모두 보존한다.
- 재생 도구(아카이브 → Redis/Influx 재적재)는 후속 스펙이다.

## 4. 검증
네트워크 없음 — S3 는 `put(key, body)` 시그니처의 fake, 시계는 주입한다. CI 에 AWS 자격증명이 없으므로 테스트가 실제 S3 를 만지면 실패해야 정상이다.
- 기록 함수 1회 → 버퍼에 줄 1개. 줄을 파싱하면 키가 정확히 `exchange`·`source`·`receivedAt`·`raw` 4개이고 이 순서다.
- JSON 페이로드는 `raw` 가 객체/배열이고, 줄에서 `raw` 부분을 잘라내면 **입력 문자열과 바이트가 같다**(공백·숫자 표기 보존 — `1.50` 과 `{"a": 1}` 처럼 재직렬화하면 달라지는 입력으로 고정).
- JSON 이 아닌 페이로드(`<html>…`)는 `raw` 가 문자열이고 원문과 같다.
- 60초 경과 → 버퍼가 닫혀 객체 1개, 키가 `raw/exchange=<id>/dt=…/hh=…/….jsonl.gz` 이고 시각이 첫 줄 `receivedAt` 의 UTC 와 일치한다.
- 비압축 32MB 도달 → 60초 전에 닫힌다. 같은 분에 객체가 둘 이상 생겨도 키가 겹치지 않는다(ms 포함).
- 거래소가 다르면 객체가 다르다. 빈 버퍼는 객체를 만들지 않는다.
- gunzip 한 줄 수 = 기록 호출 수, 줄 순서 = 호출 순서. 같은 버퍼를 두 번 직렬화한 바이트가 같다.
- 업로드 실패 → 대기열 머리에 남고 워커가 같은 키를 다시 올린다, 실패 로그에 연속 횟수, 성공 후 0 으로 돌아간다. 실패 중 닫힌 다른 거래소 객체는 뒤에서 기다렸다가 순서대로 올라간다.
- 대기열이 상한을 넘으면 가장 오래된 객체가 버려지고 에러 로그에 그 키가 남는다. 새 객체는 유지된다.
- 업로드가 멈춰 있어도(put 이 오래 걸리는 fake) 닫기 회차는 계속 돈다 — 32MB 에 닿은 버퍼가 그 회차에 닫혀 대기열에 들어간다.
- fake 가 예외를 던져도 기록 함수는 돌아오고 닫기 회차·워커는 이어간다.
- 닫기 회차 한 번이 예외로 끝나도(gzip 스레드 실행이 예외를 던지는 fake) 예외 로그 1줄 뒤 다음 회차가 돌아, 닫는 조건을 만족한 버퍼가 닫혀 올라간다.
- 실패 재시도 간격 안에 다른 객체가 대기열에 들어와도 머리 객체의 재시도는 앞당겨지지 않는다 — 간격이 지나기 전 업로드 시도 횟수는 1.
- `S3_BUCKET` 없이 기동 → 비활성·경고 로그, 스트림에 넘겨진 기록 함수가 무동작 함수(`noop_record`)이고, `/health` 200.
- `S3_BUCKET` 은 있는데 자격증명이 없어도 기동 성공 — `marketlens.main` 의 ERROR 로그는 HeadBucket 1줄뿐(전체 개수 1), 스트림에는 아카이브의 기록 함수가 넘겨지고, 그 뒤는 워커 로그로만.
- `S3_REGION` 이 빈 값이면 기본 리전으로 클라이언트를 만든다. 클라이언트 생성이 예외를 던져도 `/health` 200, 에러 로그 1줄, 스트림에 넘겨진 기록 함수는 무동작 함수.
- 재생: 아카이브 줄의 `raw` 를 001 의 업비트 호가 해석 규칙에 다시 넣으면 원래 만들어졌던 행과 같다(해석기가 순수 함수임을 이 테스트가 고정한다). 바이낸스 depth20 줄도 같다(012).
- 종료 시 열린 버퍼가 닫혀 업로드 시도가 1회 일어난다.
- 업로드가 진행 중일 때(느린 put) 종료 → 진행 중이던 객체와 종료 시 닫힌 객체가 **각각 정확히 1회** 올라가고 키가 겹치지 않는다.
- 종료 데드라인이 지나면 aclose 는 데드라인 안에 돌아오고 대기열은 비며, 남은 업로드 스레드는 데몬이다.
- 수동: 로컬 `~/.aws` + `S3_BUCKET` 으로 기동 → 약 60초 뒤 `aws s3 ls s3://<bucket>/raw/ --recursive | tail -3` 에 거래소 3곳 객체. `aws s3 cp <key> - | gunzip | head -2` 두 줄이 §3.4 모양. 1분 객체 크기와 초당 줄 수를 §5 에 기록한다(§3.5 추정치 대체). 없는 버킷으로 기동하면 객체마다(1초 간격) 실패 로그가 찍히되 `/spreads` 는 계속 갱신. EC2 배포 후 객체가 쌓이는지 확인.

## 7. 실행 보고 (실행 세션이 채움)
- 만든 것 (파일 목록): `server/app/core/s3.py`(boto3 를 import 하는 유일한 곳 — `S3Uploader.put`·`head_bucket`, 로그 없음), `server/app/core/raw_archive.py`(`format_line`·`object_key`·`pack`, `RawArchive` — `record` 계약 구현·거래소별 버퍼·단일 FIFO 대기열·매초 닫기 회차·업로드 워커 스레드·종료 5초), `server/app/core/config.py`(빈 `S3_REGION` → 기본 리전), `server/app/main.py`(lifespan 배선 — 클라이언트 생성·HeadBucket 각각 에러 1줄, 스트림이 닫힌 뒤 `aclose`), `server/tests/test_raw_archive.py`(25개), 문서 `docs/context/status.md`·`architecture.md`·`db.md`, `CLAUDE.md`.
- 추측한 지점 (묻지 않고 정한 사소한 것) / 실행 중 함께 고친 스펙 절:
  - §3.4 — `raw` 를 그대로 이어 붙이는 조건 3개(유효 JSON·최상위 객체/배열·줄바꿈 없음)를 확정. 스칼라 JSON·pretty-printed JSON·빈 문자열은 문자열로 감싼다.
  - §3.5 — "60초 경과" 의 기준을 첫 줄 `receivedAt` 과 닫기 회차 시계의 차이로, 닫는 주체를 닫기 회차 하나로 확정(32MB 는 다음 회차에 닫힌다). 닫기 회차가 업로드와 독립이라는 문장과 열린 버퍼 상한(32MB + 1초치)을 명시.
  - §3.6 — 대기열을 거래소 합산 단일 FIFO 로 확정. 업로드 주체를 워커 스레드 하나로, 대기열 접근을 잠금 직렬화로 확정 — 선택지는 ① 회차마다 `to_thread` 로 gzip+업로드를 한 번에(종료 시 진행 중 스레드와 강제 닫기 스레드가 같은 대기열을 동시에 만져 중복 업로드·유실이 가능하고, 업로드가 느리면 닫기도 멈춘다) ② 종료 플래그 + 진행 중 회차 join(느린 put 하나가 5초 데드라인을 넘긴다) ③ 닫기 회차와 업로드 워커 분리 + 잠금(추천 — 손이 하나라 중복·유실이 구조적으로 없고, 닫기 주기가 S3 상태와 무관하며, 워커가 데몬이라 종료를 붙들지 않는다). 실패 재시도 간격 1초. 종료 순서(스트림 닫힌 뒤, 009 인계 비우기와 직렬)와 기동 시 HeadBucket 실패 로그 정확히 1줄(업로더 모듈은 로그를 찍지 않고 main 이 원인을 붙여 1줄)을 명시.
  - §3.6 — 닫기 회차 태스크는 회차 안 예외(스레드 실행기 종료 등)를 로그 1줄로 삼키고 다음 회차를 돈다 — 009 Flusher 와 같은 루프 공통 규칙. 태스크가 죽으면 기록은 계속 붙는데 버퍼가 닫히지 않아 메모리가 무한히 자라기 때문이다.
  - §3.6 — 실패 뒤 재시도 대기는 `time.monotonic` 데드라인까지 반복 대기로 확정 — 선택지는 ① 조건변수 한 번 대기(다른 거래소 객체가 들어올 때마다 깨어나 1초 전에 재시도한다 — 운영에서 분당 수 회 추가 시도) ② 데드라인 반복 대기, 종료만 조기 탈출(추천 — 스펙의 '1초 뒤' 가 그대로 성립하고 종료 지연도 없다).
  - §3.2 — 빈 `S3_REGION` 은 기본 리전(boto3 는 빈 문자열을 즉시 거부한다), S3 클라이언트 생성 실패는 에러 1줄 + 비활성으로 확정 — 원문 아카이브의 어떤 실패도 기동을 막지 않는다는 §3.6 원칙의 연장.
  - §2·§3.1 — `S3_BUCKET` 배포 가드의 원본은 007 스펙 본문이 아니라 `.github/workflows/deploy.yml` 이므로 그 파일을 가리키게 고쳤다.
  - 코드 내부(동작 불변): 기록 함수가 `json.loads` 로 유효성을 판단하므로 프레임마다 파싱이 2회(커넥터 1회 + 여기 1회) 일어난다 — 초당 1~2MB 에서 수십 ms/초 수준. SDK 재시도 "2회" 는 botocore `max_attempts=3`(standard) 로 옮겼다. 테스트용 관찰자 `buffered(exchange)`·`pending`·`consecutive_failures` 와 `run_once(force_close=)`(닫은 객체 수를 돌려준다), 주입값 `retry_interval_sec`·`drain_deadline_sec` 를 공개했다. 닫기 회차가 취소돼도(종료) 진행 중인 gzip·넣기는 끝까지 가고 `aclose` 가 그것을 기다린 뒤 강제 닫기를 한다. "자격증명 없이 기동" 테스트는 실제 boto3 를 쓰되 env(`AWS_EC2_METADATA_DISABLED` 등)로 탐색을 막아 네트워크 없이 즉시 실패시킨다. 실패 로그는 warning(업로드·종료 버림)·error(상한 버림·HeadBucket·클라이언트 생성) 레벨이다.
