# 080 — quiet-reconnects

상태: DONE | 의존: 011(health — 실패 구간·`/health/collect`·수집 상태 탭), 047(perp-hyperliquid — 3샤드·구독 한도·구독 속도·핑), 025(slack-alerts — 60초 발생 알림)

> 이 문서는 이 기능이 **지금 어떻게 동작해야 하는지**를 적는다. 동작이 바뀌면 이 문서를 직접 고치고, 같은 PR 에서 코드·테스트도 맞춘다(CLAUDE.md §4·§6). 사람이 끝까지 읽는 문서다 — 코드를 산문으로 옮기지 않는다.
> 구현 구조(클래스·함수·파일 내부)는 실행 세션의 몫이다. 여기엔 **무엇이 어떻게 동작해야 하는가**만 쓴다.

## 1. 목적
2026-10-17 운영 `/health/collect` 의 24시간 실패 구간은 63건이었고, 그중 62건이 2초 안에 끝났다(잃은 시간 합 86초). 10-09(OKX·perp 원천 추가) 전에는 하루 3~15건이던 것이 40~106건이 됐고, 사람 눈에는 "자꾸 죽는다" 로 보인다. 이 스펙은 두 가지를 한다.
1. Hyperliquid 가 약 3시간마다 `1000 Expired` 로 닫는 소켓을 **닫히기 전에 새 소켓으로 갈아탄다** — 끊김 자체가 생기지 않는다(하루 약 21건 → 0).
2. 5초 안에 다시 붙은 연결 끊김(`network`)은 **'짧은 재연결'** 로 따로 세고, 실패 구간 목록·카드의 최근 에러·타임라인·로그에서 접는다. 거래소마다 24시간 횟수 하나로 보인다.

## 2. 범위
- 만드는 것: Hyperliquid 샤드 소켓 교대(§3.1), `/health/collect` 의 짧은 재연결 분류와 응답 키 `reconnects24h`(§3.2), 수집 상태 탭 카드·로그의 재연결 줄과 관리자 수집 띠 툴팁(§3.3).
- 하지 않는 것: 추적기 기록 규칙(011 §3.3 — 열기·세기·닫기·kind 전환)·Influx `collect_fail` 쓰기·복원(011 §3.4)·Slack 알림 기준(025 — 60초)·`successRate1h` 계산. 다른 거래소의 끊김 원인(OKX·비트겟·바이낸스 "no close frame") 고치기 — 원인이 거래소·망 쪽이라 이 스펙은 표시만 바꾼다. 관리자 화면(029·066)의 끊김 띠·끊김 목록·시간별 성공률 — `outages` 를 읽는 그림은 그대로 두고, 접힌 구간만큼 줄어든다.
- 바꾸는 기존 것: 047 §3.3 스트림(교대 추가). 011 §3.5 응답(`outages`·`openOutage`·`lastError` 의 대상, 키 하나 추가)·§3.8 탭(카드 한 줄·로그 한 줄).

## 3. 동작

### 3.1 Hyperliquid 소켓 교대 (047 §3.3 에 더한다)
운영 기록(10-17, 샤드 3개 × 6번): 서버는 연결을 연 지 **168~180분** 뒤 `received 1000 (OK) Expired` 로 닫는다. 그 사이에 다른 이유로 끊겨 다시 붙으면 다음 Expired 도 그 새 연결부터 다시 센다 — 연결 나이 기준이다. 지금은 닫힐 때마다 1초 백오프 + 다시 구독(샤드당 약 120구독 ÷ 초당 20 = 약 6초) 동안 그 샤드 코인의 호가가 멈춘다.
- 샤드 소켓이 열린 지 **150분**(최소 관측 168분에서 18분 여유)이 되면 교대한다: 새 소켓을 열고 → 새 소켓의 수신을 바로 시작하고(밀린 프레임으로 서버가 끊지 않게) → 그 샤드 배정 코인 전부를 047 과 같은 규칙(한 메시지에 구독 하나, 초당 20개)으로 새 소켓에 구독하고 → 그 샤드의 현재 소켓을 새 것으로 바꾸고(핑도 새 소켓으로) → 옛 소켓을 닫는다. 겹치는 몇 초 동안 두 소켓의 프레임이 모두 행에 들어간다 — 같은 시세이고 오래된 호가는 046 §3.4 대로 버려진다. 원문 싱크(010)에는 둘 다 남는다.
- 교대는 스트림 전체에서 **한 번에 하나**다 — 세 샤드는 거의 같은 때 열려 같은 때 150분이 되는데, 동시에 구독하면 초당 60개로 메시지 한도(분당 2,000)를 넘는다.
- 구독 한도: 교대하는 동안 그 샤드의 구독이 두 벌이다. (모든 샤드의 지금 구독 수 + 이 샤드 배정 코인 × 2)가 **1,000**(IP 한도)을 넘으면 교대하지 않고 경고 1줄 — 그 샤드는 예전처럼 서버가 닫을 때 다시 붙는다(§3.2 대로 짧은 재연결로 접힌다). 지금은 178 코인 → 356 + 120 = 476.
- 실패: 새 소켓 열기 실패, 구독 중 새 소켓이 닫힘, 보내기 예외 → 새 소켓을 닫고 옛 소켓을 그대로 쓴다. 경고 1줄, **5분** 뒤 다시 교대한다. 교대 중 옛 소켓이 먼저 닫혀도(서버의 Expired 가 앞당겨진 경우) 새 소켓 구독이 끝나면 그대로 갈아탄다 — 옛 소켓의 오류는 구간이 되지 않는다. 교대 중 두 소켓이 모두 닫히면 보통의 끊김(047 — 백오프 재연결)이다.
- 교대 중 샤드 상태는 계속 '연결됨'이다(판정 성공). 바꾼 시각이 그 샤드의 새 구독 시각(`connected_since`)이다. 교대가 끝나면 다음 교대는 다시 150분 뒤.
- 교대 중 재조정(60초 주기·우주 변경)은 그 샤드에서 교대가 끝날 때까지 기다린다. 교대가 끝나면 새 소켓 기준으로 차이를 맞춘다.
- 로그: 교대 성공 INFO 1줄(샤드 번호·구독 수·걸린 초). 실패·건너뜀 WARNING 1줄.

선택지와 고른 이유(2026-10-17): (a) Expired 를 실패로 세지 않기 — 목록은 줄지만 닫힐 때마다의 약 6초 호가 멈춤은 그대로이고, 그 일은 §3.2 가 이미 한다. (b) 닫히기 전에 갈아타기 — 끊김·호가 멈춤·`collect_fail` 쓰기가 모두 사라진다. 대가는 겹치는 몇 초의 구독 두 벌인데 한도의 절반도 안 된다. (b) 를 골랐다. 서버가 나이 기준을 바꾸면(150분보다 빨리 닫으면) 예전처럼 다시 붙고 §3.2 로 접힌다 — 놓치는 것은 없다.

### 3.2 `GET /health/collect` — 짧은 재연결 (011 §3.5 에 더한다)
**짧은 재연결** = 다음을 모두 만족하는 구간.
- `kind` 가 `network`(연결 끊김·연결 실패). `stale_stream`(30초 무수신 뒤에야 열리므로 실제 손실이 30초 넘음)·`timeout`·`rate_limit`·`banned`·`unavailable`·`bad_request`·`bad_response` 는 짧아도 그대로 보인다 — 거래소가 무언가를 말한 경우다.
- 길이 ≤ **5초**: 닫힌 구간은 `endedAt − startedAt`, 진행 중이면 `now − startedAt`. 5초는 011 `state` 의 `stale` 경계와 같다 — 5초 안의 끊김은 카드 상태도 `ok` 그대로다.
- 같은 거래소의 다른 구간과 맞닿지 않는다(다른 구간의 `endedAt` 이 이 구간의 `startedAt` 이거나 그 반대가 아니다). kind 전환(011 §3.3)으로 잘린 조각은 더 긴 장애의 일부라 접지 않는다.

진행 중이고 5초 이하인 `network` 구간은 아직 짧은 재연결인지 모르지만 같이 접는다 — 5초가 지나면 그때부터 보인다(5초 폴링이라 화면에서 깜빡이지 않는다).

응답:
- `outages`·각 거래소의 `openOutage`·`lastError` 는 짧은 재연결을 **뺀** 구간으로 만든다.
- 각 거래소에 `reconnects24h`(정수) — 메모리의 24시간 구간 중 닫힌 짧은 재연결 수(진행 중은 세지 않는다).
- `successRate1h`(거래소별·최상위)는 그대로 **모든** 구간으로 센다 — 잃은 초는 잃은 초다(하루 1~2초라 소수 1자리에서 거의 안 보인다).
- 추적기·Influx·Slack 은 그대로다 — 분류는 응답을 만들 때만 한다. 재기동 뒤 복원된 구간도 같은 규칙으로 나뉜다.

```jsonc
{ "exchange": "okx", "state": "ok", "lastSuccessAt": 1792…, "markets": 224, "successRate1h": 100.0,
  "openOutage": null, "lastError": null, "reconnects24h": 14 }
```

근거(2026-10-17 16:32 KST 운영 응답 63건으로 셈): 짧은 재연결 58건(전부 `network`, 1~2초)이 빠지고 5건이 남는다 — `stale_stream` 18초 1·`timeout` 3(perp REST 읽기 시간 초과 2·바이빗 pong 없음 1)·`unavailable` 502 1. §3.1 로 Hyperliquid Expired 21건은 구간 자체가 생기지 않는다. 하루 40~106건이던 목록이 한 자릿수~십여 건이 된다.

### 3.3 수집 상태 탭 (011 §3.8 에 더한다)
- 거래소 카드: `최근 에러` 줄 아래 `재연결 24h` 줄 — `{reconnects24h}회`, 0 이면 `–`. 색은 보통 글자(주의 색 아님).
- 로그 `최근 실패 구간`: 실패 구간 행 뒤, `서버 시작` 행 앞에 회색 칩 `재연결` 행 1개 — 시각 칸 `24h`, 거래소 칸 `전체`, 내용 `5초 안에 다시 붙은 연결 끊김 {합}회 · 목록에서 접음 · {거래소 이름 횟수, 많은 순, ' · ' 로 이음}`. 합이 0 이면 행이 없다. 실패 구간이 없고 재연결만 있으면 `최근 24시간 실패 없음` 줄과 재연결 행이 같이 보인다.
- 타임라인은 `outages` 만 그린다 — 짧은 재연결 막대는 없다.
- 관리자 수집 원천 띠(066 — 개요·서버 페이지): 원천 정상 띠의 툴팁에 `재연결 24h · {n}회 · 5초 이하` 줄, 0 이거나 키가 없으면(080 전 서버) 줄이 없다. 공개 화면의 수집 상태 탭은 2026-10-16 부터 숨겨져 있어 지금 사람이 보는 곳은 이 띠다.

## 4. 검증
- 교대(가짜 소켓·가짜 sleep): 150분 타이머가 풀리면 새 소켓이 열리고 배정 코인 전부를 구독하고 옛 소켓이 닫힌다. 연결 시도는 둘(처음·교대)뿐이고 끊김 판정·백오프가 없다. 교대 뒤 시세는 새 소켓에서 행으로 들어간다. 교대 뒤 핑은 새 소켓으로 나간다.
- 교대 실패: 새 소켓 열기 예외 → 옛 소켓 유지·5분 뒤 재시도. 구독 중 새 소켓이 닫히면 옛 소켓 유지.
- 교대 중 옛 소켓이 닫혀도 새 소켓으로 이어지고, 판정은 계속 성공이다.
- 구독 한도: (지금 구독 + 배정 × 2) > 1,000 이면 새 소켓을 열지 않는다.
- 교대는 한 번에 하나: 두 샤드가 함께 150분이 돼도 두 번째 교대의 새 소켓은 첫 교대가 끝난 뒤 열린다.
- 기존 047 테스트(핑·pong 없음·말없는 닫힘·백오프·종료) 그대로 통과.
- 짧은 재연결: `network` 1초 닫힌 구간은 `outages`·`lastError` 에서 빠지고 `reconnects24h` 1. 6초면 남는다. `stale_stream`·`timeout` 1초는 남는다. kind 전환으로 맞닿은 `network` 조각은 남는다. 진행 중 `network` 3초는 `openOutage` null·`outages` 에 없음, 6초면 보임. `successRate1h` 는 짧은 재연결의 초도 센다.
- node(관리자): `reconnects24h` 가 있으면 띠 툴팁에 줄 하나, 0·없음이면 없음.
- 수동(운영 배포 뒤 하루): `/health/collect` 의 `outages` 길이가 한 자릿수~십여 건, Hyperliquid `reconnects24h` 가 0 근처, collect 로그에 `소켓 교대` INFO 가 샤드마다 약 2시간 반 간격.
