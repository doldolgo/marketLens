## 1. 목적
해외 거래소 네 번째로 **OKX(`okx`) USDT 현물**을 붙인다. 끝나면 스프레드 표에 `fx = okx` 행이 생겨 트레이더가 같은 코인의 바이낸스·바이빗·비트겟·OKX 김프를 나란히 보고, OKX 입출금 상태까지 표에서 본다. 기록 탭의 해외 카드에 OKX 가 실데이터로 생긴다.
비트겟처럼 시세는 WebSocket 만, REST 는 심볼 목록(매초)과 입출금 상태(60초)에만 쓴다. 커넥터는 012·019·020 과 **코드를 공유하지 않고** 규칙만 같다(architecture.md 원칙). OKX 공식 문서는 API v5 기준이며 2026-10-08 에 확인했다. 입출금 상태는 인증이 필요한 엔드포인트뿐이라 **키 3개(API 키·시크릿·패스프레이즈)** 가 있어야 조회된다.

## 2. 범위
- 만드는 것: OKX 스트림 커넥터(샤드 3개·구독 재조정·핑·재연결·정체 판정), 심볼 목록 REST 조회, OKX 입출금 조회기(인증, 키 3개), 테스트. 라이브러리 추가 없음(`websockets`·`httpx`·표준 `hmac`·`base64`).
- 바꾸는 기존 것:
  1. **마켓 우주(001 §3.2)** — 해외 원천이 넷이 된다. 우주 = `(업비트 KRW base ∪ 빗썸 KRW base) ∩ (바이낸스 ∪ 바이빗 ∪ 비트겟 ∪ OKX USDT base)`. 우주가 확정될 때마다 해외 원천 각각에 `set_universe(우주)` 를 넘기고, 자기 맵에 없는 base 는 그 커넥터가 무시한다(019 §2-1 규칙 그대로).
  2. **거래소 목록 6곳** `upbit·bithumb·binance·bybit·bitget·okx` 고정 순서 — 틱 판정(011), `/health/collect` 의 `exchanges[]`, `/refresh` 의 `snapshots[]`, 입출금 반영 순서, 관리자 화면(036)의 수집 카드 순서 전부.
  3. **입출금(006)** — 조회기 6종. OKX 는 env `OKX_API_KEY`·`OKX_SECRET_KEY`·`OKX_PASSPHRASE` 셋이 전부 있어야 조회하고, 하나라도 비면 바이낸스·바이빗과 같은 방식으로 경고 1줄·전 코인 `unknown`(`OKX_API_KEY / OKX_SECRET_KEY / OKX_PASSPHRASE 가 비어 있습니다.`). `.env.example` 과 dev-setup.md 키 표에 세 줄이 는다.
  4. **`/history/premium`·`streaks`·`streaks/bulk`·`candles`** 의 `fx` ∈ {`binance`, `bybit`, `bitget`, `okx`}(기본 `binance` 그대로). 그 밖의 값은 지금처럼 422. `/history/events` 는 `fx` 필터가 없어 OKX 사건이 함께 나온다.
  5. **web** — 표시명 `okx → OKX`(스프레드 표의 "비교 해외 거래소" 체크박스 목록에 `OKX` 를 Bitget 다음에 넣는다 — 이 목록 밖 이름은 URL 필터에서 버려지므로 빠뜨리면 체크박스가 안 생긴다), 기록 탭 해외 카드에 OKX 를 **실데이터**로 추가(Bitget 다음). 관리자 화면 수집 카드 목록에 `okx` 를 마지막에. 랜딩·`/kimp-chart`·`/kimp-history`·대시보드 메타 설명의 "바이낸스·바이비트·비트겟" 문구를 "바이낸스·바이비트·비트겟·OKX" 로, "해외 거래소 3곳"·"다섯 거래소" 류 숫자를 4곳·여섯 거래소로, 정적 페이지의 표시명 사전에 `okx → OKX`(파일별 위치는 §6).
  6. 004 의 거래소 레지스트리에 `okx`(표시명 `OKX`)를 더해 `/orderbook/okx`·`/slippage/okx` 가 열린다 — §4 수동 확인이 이 경로를 쓴다.
- 하지 않는 것: 004 의 나머지 API(`/premium`·`scan`·`matrix`·`/arbitrage`)의 해외 선택(바이낸스 고정 — 기존 빚 그대로). 백필 스크립트(binance 만). `/spreads` 행 계약(19키 그대로 — okx 행은 `fx` 값만 다르다). 사건(013)·1분봉(014)·틱 저장(009)·원문 아카이브(010)·표 푸시(017)·일 변동(026) — 거래소 id 나 틱 행 단위로 돌아 코드 변경 없이 okx 가 흘러든다(§3.7). 선물·OKX 파생(Hyperliquid 선물은 별도 스펙). 전체 깊이 `books` 채널과 로컬 북(§3.2 에 이유). 지역 도메인(us·eea·tr)과 SBE 바이너리 채널.

## 3. 동작

### 3.1 읽는 계약 (복사)
- 001 §3.3·§3.5-1: 행 = `(exchange, base)` 당 `quote`·`native_symbol`·`price`·`price_timestamp`·`asks`·`bids`(가격 > 0 이고 유한·잔량 > 0 이고 유한한 단계만, 누적 1,000,000 USDT 도달 단계까지, 최소 1단계)·입출금 3필드(물려받음)·`updated_at`. 거래소별 스트림 상태 `{connected, last_message_at, last_error, subscribed, url, connected_since}`.
- 001 §3.2: 해외 심볼 원천 계약 `id` / `refresh(client) -> int`(REST 1회, 실패는 거래소 예외) / `bases() -> set[str]` / `set_universe(bases)`(매초·`/refresh`·기동, 배정이 같으면 무동작). `main.py` 가 우주에 목록 `[binance, bybit, bitget, okx]` 로 꽂는다.
- 001 §3.7: 받은 모든 프레임과 REST 본문은 원문 싱크 `record(exchange, source, received_at_ms, payload, key)` 로 — 행·상태 갱신 전에, 텍스트 그대로. 시세 프레임은 `key` = `orderbook:<심볼>`·`trade:<심볼>`(원본 instId 그대로, 예 `BTC-USDT`), 매초 오는 심볼 목록 본문은 `symbols:all`, 구독 응답·`pong`·`notice`·깨진 프레임·핸드셰이크 거부 본문·입출금 본문은 `key=None`. 010 이 `key` 있는 줄을 분당 마지막 1건으로 솎는다.
- 011 §3.2: 실패 8종 `timeout network rate_limit banned unavailable bad_request bad_response stale_stream`. 매 틱 거래소마다 판정해 추적기에 넘긴다.
- 006 §3.1·§3.5 + architecture.md core 계약: 입출금 조회기는 `refresh_if_due(client, force=False)` / `apply(rows, exchange)` / `availability()` / `warnings()` / `failed()`. 코인 상태 `open / closed / unknown`, **`unknown` 을 열림으로 읽지 않는다**. 네트워크 = `{code, name, dep, wd}`(code 대문자, name 은 표시명), 실패 회차는 직전 값을 지키지 않고 `unknown` 으로 덮는다. 요청 타임아웃 10초, 본문은 성공·실패 모두 원문 싱크로. 네트워크 판정(국내 기준·정규화·동일 체인 쌍)은 006 §3.6~3.7 그대로.

### 3.2 스트림
- 엔드포인트 `wss://ws.okx.com/ws/v5/public`(공개 채널, 로그인 없음. 포트를 적지 않는다 — `:8443` 은 2026-10-31 에 닫힌다). 구독 `{"op":"subscribe","args":[{"channel":"<채널>","instId":"<instId>"}, …]}`, 해지는 `op:"unsubscribe"`. 호가·체결 채널은 `instType` 을 받지 않고 `instId` 만 쓴다. 응답 `{"event":"subscribe","arg":{"channel":"books5","instId":"BTC-USDT"},"connId":"…"}` 은 **arg 하나마다 1개**가 오고 시세로 세지 않는다. 거부는 `{"event":"error","code":"60012","msg":"…","connId":"…"}`(code 는 문자열) → `bad_request`(message 에 `code`·`msg`)로 실패하고 재연결한다. `{"event":"notice","code":"64008",…}` 는 서비스 업그레이드 60초 전 통지다 — 시세가 아니고(`key=None`) 디코드 실패도 아니며, 경고 1줄만 남긴다(끊기면 보통의 재연결).
- 한도(공식 문서): 연결 요청 **IP 당 초당 3회**, **구독·해지 요청 연결당 시간당 480회**, 한 구독 요청의 `args` **총 64KB 이하**. 30초 동안 구독이 없거나 데이터가 안 오면 서버가 끊는다(Close 4004). 연결당 채널 수 상한·초당 송신 메시지 상한·24시간 강제 종료는 문서에 없다(초과하면 Close 4008 로 끊긴다는 것만) — EC2 실측 항목.
- 심볼마다 두 채널. **`books5`** — 위 5단계 스냅샷, 변화가 있을 때 **100ms 마다** 통째 온다. 페이로드 `{"arg":{"channel":"books5","instId":"BTC-USDT"},"data":[{"asks":[["<가격>","<잔량>","0","<주문수>"],…],"bids":[…],"instId":"BTC-USDT","ts":"<ms 문자열>","seqId":<정수>}]}` — `action` 이 없고, 원소의 셋째 값은 폐기된 필드라 항상 `"0"`, 넷째는 그 가격의 주문 수(쓰지 않는다). `asks` 오름차순·`bids` 내림차순, `data` 는 원소 1개. **`trades`** — 체결마다 `{"arg":{"channel":"trades","instId":"BTC-USDT"},"data":[{"instId":"BTC-USDT","tradeId":"…","px":"…","sz":"…","side":"buy|sell","ts":"<체결 ms>","count":"3","source":"0","seqId":…}]}`. 한 메시지가 테이커 주문 하나의 체결 여러 건을 묶는다(`count`). 구독 직후 과거 체결 스냅샷은 문서에 없다(오더라도 §3.4 의 "오래된 체결 무시" 가 막는다).
- 왜 `books5` 인가: 전체 깊이 `books`(400단계)는 100ms 마다 update 가 와 심볼마다 로컬 북을 유지해야 하고, 우주 300 종목이면 초당 3,000 update 에 400단계 북 정렬이 따른다 — 비트겟 `books` 때 collector CPU 47% 를 먹어 되돌린 전례(020 §3.2)가 있다. `books50-l2-tbt`·`books-l2-tbt` 는 VIP4 이상만 구독할 수 있다(아니면 code 64003). 그래서 로그인 없이 받을 수 있는 가장 깊은 스냅샷 채널은 `books5` 뿐이다. 표는 체결 규모 $1,000 기준이라 주요 코인은 5단계로 충분하고, 얇은 코인은 1,000,000 USDT 누적 전에 단계가 끝나 001 규칙대로 있는 단계까지만 싣는다. **OKX 행의 호가는 최대 5단계**다 — `/orderbook/okx` 도 5단계까지만 준다(빚, §6 status.md). 체결가는 체결이 있을 때만 오는 `trades` 를 쓴다 — 바이낸스 miniTicker·바이빗 publicTrade·비트겟 trade 와 의미가 같다. `trades-all`(체결 1건씩)은 다른 URL(`/ws/v5/business`)이라 쓰지 않는다.
- **핑**: 문서는 "응답을 받을 때마다 30초보다 짧은 타이머를 걸고, 만료되면 문자열 `ping` 을 보내라" 고 한다. 규칙 — 샤드마다 **마지막 수신(시세든 응답이든 `pong` 이든)에서 20초가 지나면 문자열 `ping`** 을 보내고(JSON 아님), 응답은 **문자열 `pong`** 이며 시세가 아니다(`key=None`, JSON 디코드 실패로 세지 않는다). **보낸 핑의 pong 이 10초 안에 안 오면 끊고 재연결**한다 — 그 샤드의 마지막 오류는 `timeout`(message 에 "pong 없음"). 시세가 계속 오는 샤드는 핑을 보내지 않는다(서버의 30초 기준은 어느 방향이든 데이터가 흐르면 충족된다). 라이브러리 keepalive(제어 프레임 ping)는 끈다 — 문서에 없다.
- 시세가 아닌 프레임(구독 응답·`notice`·`pong`·깨진 JSON·맵에 없는 심볼)은 원문 싱크에만 남기고 시세 수신으로 세지 않는다. 판별: 텍스트가 `pong` 이면 pong, JSON 에 `event` 키가 있으면 응답(`error` 면 거부, `notice` 면 통지, 그 밖(`subscribe`·`unsubscribe`)은 응답), `arg`·`data` 가 있으면 시세. 둘 다 아니면 디코드 실패로 센다.
- 재연결은 지수 백오프 1·2·4…30초, **구독 뒤 그 샤드의 첫 시세 프레임**에서 1초로 리셋(001·012·019·020 과 같다). 핸드셰이크 HTTP 거부는 §3.8 규칙. 샤드 3개가 동시에 재연결해도 IP 당 초당 3회 안이다 — 백오프 지터는 두지 않는다. 재연결은 새 연결이므로 시간당 480회 구독 예산도 새로 시작한다.

### 3.3 심볼 목록과 샤딩
- 심볼 목록: `GET https://openapi.okx.com/api/v5/public/instruments?instType=SPOT`(인증 없음) → `data[]` 중 `state == "live"` 이고 `quoteCcy == "USDT"` 인 것(`state` 는 `live / suspend / preopen / test / post_only / rebase` — `preopen` 은 `listTime` 에 `live` 로 바뀐다, `test` 는 거래 불가 테스트 페어). base = `baseCcy`, 심볼 = `instId`(예 `BTC-USDT`). 페이지네이션 없음. 봉투 `{"code":"0","msg":"","data":[…]}` — **HTTP 200 이어도 `code != "0"` 이면 실패**(§3.8). 한도 IP 당 2초에 20회 — **매초** 갱신(001 §3.2)은 그 10%. 본문은 `rest:/api/v5/public/instruments` 로 원문 싱크(`symbols:all`). 실패 시 직전 목록 유지 + 경고. 본문 크기·파싱 시간은 미확인(EC2 실측 항목). 도메인은 2026-05-20 부터 문서가 쓰는 `openapi.okx.com` 이다(`www.okx.com` 도 계속 되지만 문서 기준을 따른다).
- **본문이 직전과 같으면 파싱하지 않는다(001 §3.2 결정).** OKX 봉투에는 매 응답 바뀌는 시각 필드가 없어 **본문 전체 바이트**를 직전에 심볼 맵까지 만든 200 응답과 비교한다. 같으면 원문 기록만 하고 파싱·맵 재생성 없이 돌아온다(호출 수 1). `code != "0"` 처럼 맵을 만들지 못한 본문은 기억하지 않는다. 상장 공지 직후 `instId`·`listTime`·`state` 만 차고 나머지가 빈 문자열인 행이 올 수 있다 — `state` 가 `live` 가 아니므로 자연히 빠진다.
- base 하나에 USDT 심볼이 둘 이상이면 처음 것. 우주 base 중 맵에 없는 것은 구독 대상이 아니다. `USDT` 자신은 우주에 없다(001).
- **3 샤드**, 배정 = `crc32(instId) % 3`, 한 심볼의 두 채널은 같은 샤드 — 012·019·020 과 같은 규칙.
- 재조정 규칙은 019 §3.3 그대로: 우주 확정마다 `set_universe`, 빠진 심볼의 행은 그 자리에서 삭제, 연결된 샤드마다 원하는 구독과 실제 구독의 **차이만** 전송, 실제 구독 집합은 소켓에 묶인다, 60초마다 한 번 자동 재조정, 배정 0 샤드는 연결하지 않는다. 한 요청 `args` **50개 이하**(원소 하나 약 45바이트 → 2.3KB, 64KB 한도 안 — 개수 한도는 문서에 없어 비트겟과 같은 값으로 둔다), 요청 사이 **0.2초**. 배정 150 심볼이면 6요청·1.2초. 구독·해지 요청 수를 소켓별 최근 1시간 창으로 세어 480회의 80%(384회)를 넘으면 경고 1줄을 남기고 재조정을 다음 회차로 미룬다(020 §7 의 예산 규칙과 같다).

### 3.4 행 갱신 (로컬 북 없음)
- `books5` 는 스냅샷만 오므로 **로컬 북을 두지 않는다.** 매 호가 메시지마다 그 심볼의 행을 다시 만든다: `asks`·`bids` 를 001 규칙(가격·잔량이 0 이하이거나 유한하지 않은 단계 제거·누적 상한)으로 자른 것, `updated_at` = 수신 시각, 호가 시각 = `data[0].ts`(문자열 → 정수 ms). 가격이 `asks` 엄격한 오름차순·`bids` 엄격한 내림차순인지 한 번 훑어 확인하고, 맞으면 받은 순서 그대로(020 §3.4 의 정렬된 스냅샷 경로), 깨졌거나 가격이 겹치거나 NaN 이 끼면 정렬하고 같은 가격은 뒤 것을 남긴다.
- **호가 시각이 지금 행의 호가 시각보다 오래된 스냅샷은 버린다**(순서 뒤바뀜 방어 — 원문에는 남고 수신 시각에는 센다). `seqId` 는 쓰지 않는다 — 점검 뒤 시퀀스가 되돌아가는 경우가 문서에 있어 순서 판정에 믿을 수 없고, 스냅샷 전용 채널이라 연속성 검증이 필요 없다.
- `asks`·`bids` 가 **둘 다 빈** 메시지는 행을 지우지 않고 무시한다(수신 시각에는 센다 — 문서가 `books` 계열에 60초 무변동 하트비트로 빈 북을 보낸다고 하며, `books5` 에 오는지는 미확인이라 같은 규칙으로 막아 둔다). 한쪽만 비면 행을 저장하지 않는다(있던 행은 지운다 — 001 과 같다).
- `trades` → `data[]` 중 **`ts` 가 가장 큰 원소**의 `px` 가 `price`, 그 `ts` 가 `price_timestamp`(배열 순서를 믿지 않는다). 이미 있는 `price_timestamp` 보다 **엄격히 오래된** 체결은 무시한다(같은 ts 는 최신으로 실어 갱신). 행이 없으면 보류했다가 호가가 오면 함께 싣는다. 체결가가 없으면 mid — 이때 `price_timestamp` 는 수신 시각(012·019·020 과 같다). `source`·`count`·`side` 는 쓰지 않는다.
- 캐시 키·`native_symbol` 은 원본 `instId`(`BTC-USDT`). `arg.instId` 가 맵에 없으면 그 프레임은 버린다. 입출금 3필드 물려받기·우주 밖 버리기는 001 §3.5.

### 3.5 정체 판정 (매 틱, 샤드 단위)
019 §3.5 와 같다 — 샤드마다 `last_message_at`·배정 수·구독 시각, 조용한 시간 = 지금 − max(마지막 시세, 연결 중이면 구독 시각), 배정 0 샤드는 판정 대상 아님, 연결됐는데 **30초** 무수신 → `stale_stream`, 미연결 → `last_error.kind`, 여러 샤드가 나쁘면 가장 오래 조용한 샤드(동률이면 작은 번호), 전부 판정 없음이면 없음. `pong` 만 오고 시세가 없어도 30초면 정체다. 실패 `message` = `"OKX 스트림 정체: 샤드 2 (구독 7종목) 30초 이상 무수신"`, `url` = WS URL. `store.stream("okx")` 집계도 020 §3.5 와 같다 — 시세 프레임은 집계 `last_message_at` 만 올리고(더 클 때만), 연결·끊김·구독 변경 때 전체를 다시 집계한다.

### 3.6 입출금 상태 (006 의 여섯 번째 조회기 — 인증 API)
- `GET https://openapi.okx.com/api/v5/asset/currencies`(파라미터 없음 = 계정이 볼 수 있는 전 통화·체인). **인증 필수** — 헤더 `OK-ACCESS-KEY`(API 키)·`OK-ACCESS-PASSPHRASE`(키 만들 때 정한 패스프레이즈)·`OK-ACCESS-TIMESTAMP`(UTC ISO 8601 밀리초, 예 `2020-12-08T09:08:57.715Z`)·`OK-ACCESS-SIGN`. 서명 = `HMAC-SHA256(secret, timestamp + "GET" + "/api/v5/asset/currencies")` 의 **Base64**(질의·본문 없음). 서버 시각과 30초 넘게 어긋나면 code `50102` → `bad_request`. 한도 사용자당 초당 6회(60초 주기라 무관). 키 권한은 읽기(Read)면 된다 — 엔드포인트 단위 권한 표기는 문서에 없어 실키로 확인한다(§4 수동). IP 허용 목록은 필수가 아니다(문서는 권장).
- 키 검사·메시지는 006 바이낸스와 같은 방식이되 셋을 본다: `OKX_API_KEY / OKX_SECRET_KEY / OKX_PASSPHRASE 가 비어 있습니다.` 하나라도 비면 조회하지 않고 전 코인 `unknown`·`walletStatusAvailable` false·경고 1줄.
- 응답 `data[]` 는 **(통화, 체인) 한 쌍이 한 행**이다 — `ccy`(대문자 심볼)·`chain`(예 `USDT-ERC20`·`BTC-Bitcoin`·`ETH-Arbitrum One`)·`canDep`·`canWd`(**JSON boolean**)·`mainNet`(boolean). 같은 `ccy` 행을 모아 코인 하나로 만든다. 네트워크 = `chain` 에서 앞의 `"<ccy>-"` 를 뗀 나머지(없으면 `chain` 전체)로 `name = 그 원문`, `code = 그 원문을 대문자로 하고 공백을 뺀 것`(예 `ERC20`·`BITCOIN`·`ARBITRUMONE`), `dep = canDep`, `wd = canWd`. 코인 단위 dep/wd = 한 네트워크라도 열려 있으면 ok. `canInternal`·`depEstOpenTime`·`wdEstOpenTime`·`minWd`·`fee` 는 판정에 쓰지 않는다. 목록은 계정의 KYC 소속에 따라 다를 수 있다(문서 문장) — 어떤 코인이 응답에 없으면 그 코인은 `unknown` 이다.
- **네트워크 이름 판정(006 §3.6)**: OKX 표기(`Bitcoin`·`Ethereum`·`Solana`·`Arbitrum One`·`ERC20`·`TRC20`)는 006 의 정규화(소문자·불용어·별칭 `erc20→ethereum`·`trc20→tron`·`arbitrumone→arbitrum` 등)가 이미 덮어 별칭 추가 없이 국내 기준 네트워크와 짝이 맞는다. 실키 응답에서 정규화가 못 맞추는 표기가 보이면 006 §3.6 의 별칭 표에 더하고(스펙 문장도 같이) `test_networks.py` 에 기대값을 쓴다. 짝을 못 찾은 네트워크는 지금 규칙대로 `?` 로 남는다.
- HTTP 200 + `code != "0"` 은 실패(§3.8). 실패 회차 처리·`/refresh` 경고·`walletStatusAvailable` 은 006 §3.5 그대로. 본문은 `rest:/api/v5/asset/currencies` 로 원문 싱크(`key=None`) — **요청 헤더는 기록하지 않는다**(키·서명).

### 3.7 다른 기능에 흘러드는 것 (코드 변경 없이)
- 틱(001 §3.6-2)은 국내×해외 **전 조합**이라 `(upbit|bithumb) × okx` 행이 생긴다 → 003 표·017 푸시·013 사건·014 1분봉·024 네트워크 4상태·026 변동율·009 Influx `premium` 에 `fx=okx` 태그 값으로 들어간다. Influx 스키마(db.md)는 그대로고 카디널리티만 대략 4/3 배.
- 010 은 `raw/exchange=okx/…` 객체를 자동으로 갖는다. 011 추적기·025 Slack 알림은 거래소 문자열 키라 자동(알림 본문은 id `okx` 그대로).

### 3.8 실패 분류 — OKX REST·핸드셰이크 규칙 (011 §3.2 에 추가하는 행)
- HTTP 429 → `rate_limit`. **HTTP 200 + `code == "50011"`("Rate limit reached") 도 `rate_limit`** — 문서가 같은 코드를 200·429 양쪽에 둔다. 403 → `banned`. 5xx → `unavailable`. 그 외 4xx → `bad_request`. `Retry-After` 는 문서에 없으니 `retry_after_sec` 는 null. IP 차단 규칙은 문서에 없다.
- HTTP 200 + `code != "0"`(50011 제외) → `bad_response` 에 원문 body(`status_code` 200). 인증 오류(`50102` 시각 어긋남·`50111` 키 없음·`50113` 서명 틀림 등)는 입출금 조회기에서만 나오며 `bad_response` 로 분류하고 경고 메시지에 `code`·`msg` 를 싣는다.
- 공통(REST): httpx 타임아웃 → `timeout`, 전송 예외 → `network`, JSON 아님·`data` 없음 → `bad_response`. WebSocket: 연결 실패 → `network`, 핸드셰이크 타임아웃 5초 → `timeout`, HTTP 거부는 위 규칙, `event:"error"` → `bad_request`.

## 4. 검증
네트워크 없음 — 가짜 소켓·가짜 REST·가짜 원문 싱크(001 의 fakes 재사용).
- books5 스냅샷 → 행의 `asks` 오름차순·`bids` 내림차순 float(원소 4개 중 앞 둘만), 누적 1,000,000 USDT 에서 잘리고 첫 단계가 넘어도 1단계는 남는다. `native_symbol` 은 `BTC-USDT`, 호가 시각은 `data[0].ts` 를 정수로. 정렬돼 온 스냅샷의 행은 뒤섞인 같은 스냅샷을 정렬한 행과 같다. 가격이 겹치면 뒤 것이 남는다.
- 호가 시각이 지금 행보다 오래된 스냅샷은 무시(원문에는 남고 수신 시각에는 센다). `seqId` 가 되돌아간 스냅샷도 `ts` 가 새로우면 반영된다. `asks`·`bids` 둘 다 빈 메시지는 행을 지우지 않는다. 한쪽만 비면 행이 지워진다.
- trades 3건 중 `ts` 가 가장 큰 것이 `price`·`price_timestamp`. 현재 값보다 엄격히 오래된 체결은 무시, 같은 ts 는 갱신. 호가 전에 오면 보류, 호가 뒤에 실린다. 체결가 없으면 mid 이고 `price_timestamp` 는 수신 시각.
- 본문이 같은 instruments 200 응답이 연달아 오면 둘째는 원문 기록만 하고 파싱하지 않는다(사이에 실패 응답이 있어도 같다), 바뀐 본문에서만 파싱해 집합이 바뀐다. `code != "0"` 본문은 같은 본문이 다시 와도 다시 실패다.
- instruments 에서 `live`·`USDT` 만 심볼 집합에 든다(`suspend`·`preopen`·`test`·`post_only` 제외, 빈 `baseCcy` 행 제외). 원문 source 는 `rest:/api/v5/public/instruments`, key `symbols:all`. `code != "0"` 본문(HTTP 200)은 실패이고 직전 목록 유지.
- 우주 = 국내 합집합 ∩ (바이낸스 ∪ 바이빗 ∪ 비트겟 ∪ OKX). OKX 에만 있는 base 는 OKX 행만 생기고, 각 커넥터는 자기 맵에 없는 base 를 구독하지 않는다. 틱에 `(upbit, okx, BTC)`·`(bithumb, okx, BTC)` 행이 나온다.
- 심볼 300개 → 3 샤드, 같은 심볼은 항상 같은 샤드(해시 안정성 — 서브프로세스 2회), 두 채널 같은 샤드. 구독 요청 `args` ≤ 50, 요청 사이 0.2초, 요청 직렬화 길이 ≤ 64KB. 재조정: 새 심볼 구독·빠진 심볼 해지·행 삭제, 같은 우주 재수신은 전송 0. 시간당 구독·해지 요청 385회째는 보내지 않고 경고 1줄.
- 구독 응답은 arg 마다 1개 오고 시세로 세지 않는다. `event:"error"` → `bad_request`, message 에 code·msg, 재연결. `event:"notice"` 는 경고 1줄, 시세 아님, 디코드 실패 아님, `key=None`.
- 핑: 마지막 수신 20초 뒤 문자열 `ping`, 시세가 흐르는 동안은 보내지 않음, 문자열 `pong` 은 시세가 아니고 디코드 실패도 아니며 `key=None`. pong 이 10초 안에 없으면 재연결·`timeout`.
- 정체: 샤드 2만 30초 무수신 → `stale_stream`, message 에 "샤드 2". pong 만 오는 샤드도 30초면 정체. 미연결 샤드 → `last_error.kind`. 둘이 나쁘면 더 오래 조용한 쪽. 시세 프레임은 집계 `last_message_at` 만 올린다.
- 원문: 모든 프레임이 원문 그대로 기록 — 호가·체결 프레임은 `orderbook:BTC-USDT`·`trade:BTC-USDT`, 심볼 목록은 `symbols:all`, 구독 응답·notice·pong·핸드셰이크 거부·입출금 본문은 `key=None`. 행 갱신 전에 기록된다. 입출금 요청의 헤더는 어디에도 남지 않는다.
- 분류: 429 → `rate_limit`, 200+`code:"50011"` → `rate_limit`, 403 → `banned`, 200+`code:"50013"` 류 → `bad_response`(status_code 200), `event:"error"` → `bad_request`. 백오프 1·2·4…30, 구독 뒤 첫 시세에서 1.
- 입출금: 헤더 4개가 붙고 서명이 `timestamp + "GET" + "/api/v5/asset/currencies"` 의 HMAC-SHA256 Base64 와 같다(고정 timestamp·secret 로 기대값 비교). 키 셋 중 하나라도 비면 요청 없이 전 코인 `unknown`·경고 1줄·`walletStatusAvailable` false. `(ccy, chain)` 행 여러 개가 코인 하나로 합쳐지고 `canDep/canWd` boolean → `dep/wd`, 네트워크 `code` 는 `"<ccy>-"` 를 뗀 나머지의 대문자·공백 제거, `name` 은 원문, 한 네트워크만 열려도 코인 dep ok, 응답에 없는 코인은 `unknown`. `code != "0"` → 실패·전 코인 `unknown`·경고 1줄. OKX `chain` 표기(`BTC-Bitcoin`·`USDT-ERC20`·`USDT-TRC20`·`ETH-Arbitrum One`·`SOL-Solana`)에서 뗀 이름이 국내 기준 네트워크와 짝이 맞는다(`test_networks.py`).
- `/health/collect` 의 `exchanges` 가 6곳 순서 `upbit bithumb binance bybit bitget okx`. `/refresh` 의 `snapshots` 6항목. `/history/candles?fx=okx` 는 200, `fx=mexc` 는 422. `/orderbook/okx` 가 열리고 `depth=20` 을 줘도 5단계까지만 준다.
