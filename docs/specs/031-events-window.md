## 1. 목적
공개 `/api/history/events` 요청 하나가 읽고 내보내는 양에 위를 둔다. 지금은 기간 상한이 없어 `?start=0` 한 번이면 배포(2026-09-07) 뒤 모든 사건을 수집기가 Influx 에서 읽어 JSON 으로 만든다 — 2026-09-29 운영 실측 1일 1.8MB·6.8초, 7일 13MB·17초, 30일 28MB·33초이고 사건은 하루 6,100~11,200건씩 쌓인다. 이 경로는 평소 1 vCPU 를 80~100% 쓰는 수집 박스(c7g.medium, 2GiB)가 답하므로(028) 요청이 클수록 수집과 같은 코어·메모리를 나눠 쓴다. 끝나면 전 코인 조회는 7일, 코인 하나(`base`) 조회는 90일까지만 답하고, 넘으면 Influx 를 읽기 전에 400 이다. 기록 탭은 그 안에서만 부른다 — 기간 버튼에서 1달·3달이 빠진다.

## 2. 범위
- 만드는 것: `GET /history/events` 창 상한(`server/app/features/history/`), 기록 탭 기간 선택지와 차트 음영 조회 범위(`web/src/features/history/`), 테스트.
- 하지 않는 것 — 고르지 않은 선택지와 이유(전부 후속 후보):
  - **요청 속도·동시 요청 제한**(nginx `limit_req`·`limit_conn`). 상한을 둔 뒤에도 요청 하나가 운영에서 최대 ≈17초(7일 전 코인)라, IP 당 분당 4번만 열어 줘도(4 × 17초) 한 IP 가 코어 하나를 채운다. IP 를 바꿔 가며 부르면 소용이 없고, 같은 공유기 뒤 접속자들은 함께 막힌다. nginx 가 보는 주소는 앞단 caddy 하나라(023) IP 별로 세려면 원 IP 를 넘겨받는 설정이 새로 들고, 027 이 이 경로를 접속 로그에서 빼므로 값을 정할 근거도 없다. 요청 하나의 비용이 작아진 뒤에 본다.
  - **api 역할로 옮기기.** 진행 중 사건이 수집기 메모리에 있어(013 §3.4) api 는 Influx 만으로 진행 중을 다시 판정해야 한다. api 박스(t4g.micro, 1GiB)는 `/ws/spreads`·랜딩을 함께 답하므로 상한 없이 옮기면 위험이 그쪽으로 갈 뿐이다. 이 스펙 뒤에는 옮겨도 요청 하나의 크기가 정해져 있다 — 013·016·021·028 을 함께 고치는 일이라 따로 한다.
  - **코인별 요약 응답·페이지.** 요약(서버가 표의 코인별 수치만 보낸다)은 7일 역프 12.7MB 를 수십 KB 로 줄이지만 013 의 응답 계약과 화면 집계를 다시 쓰는 일이라 담당자 결정이고, Influx 는 여전히 창만큼 읽으므로 상한은 그대로 필요하다. 1달·3달 기간을 되살리는 조건이다. 페이지는 표가 전 사건을 모아 집계하므로 받는 총량이 같다.
  - **공유 캐시·숨은 탭 재조회 멈춤·응답 JSON 을 스레드에서 만들기** — 접속자 수에 비례하는 반복 부하는 `perf/hot-path` 작업(미커밋, 013 을 고친다)이 다룬다. 이 스펙과 독립이다(§3.4).
  - **기본 창 변경.** `start` 없으면 `end − 7일`(005·013) 그대로다. 상한과 같아 기본 요청은 늘 통과한다.

## 3. 동작

### 3.1 읽는 계약 (복사)
- 013 §3.4: `GET /history/events?start&end&dom&dir&base` — 전부 선택. `start`·`end` 는 epoch 초 0~4,102,444,800(밖이면 422), `start` 없으면 `end − 7일`(0 미만이면 0), `end` 없으면 지금+1초, `end ≤ start` 면 400 `invalid_request`. `base` 는 `^[A-Za-z0-9]{1,20}$` 이고 대문자로 바꾼다. 구간 판정 `start ≤ start_ts < end`. 응답 = Influx 의 닫힌 사건 + 수집기 메모리의 진행 중 사건. Influx 가 없거나 닿지 않으면 503 `storage_unavailable`.
- 005: 오류 본문 `{"error":{"code","message","detail"}}`, HTTP 키 camelCase.
- 014 §3.6: `/history/candles` 는 `end − start` 가 상한을 넘으면 400 `invalid_request`, 메시지 "window exceeds limit…", `detail` `{"limitSec": 상한}` 이다. 이 스펙이 같은 모양을 쓴다.
- 013 §3.5·014 §3.7(web): 기록 탭은 표·요약·로그용으로 `start = 지금 − 기간`, `end = 지금`, `dir` 을 늘 붙여 부르고, 국내 거래소를 고르면 `dom` 도 붙인다. 기간은 `1시간/4시간/8시간/12시간/24시간/3일/1주/1달/3달`(기본 1주, URL 키 `h.per`). 차트 음영용으로는 선택 심볼 `base` 와 "가장 오래된 청크 시작 ~ 지금" 을 따로 부른다 — 청크 = 360창(1m 6시간·5m 30시간·1h 15일·4h 60일·1d 360일), 과거로 끌면 청크를 더 붙인다. 둘 다 60초마다 다시 부른다.
- 028: 공개 `/api/history/events` 는 정확 일치로 수집기(`COLLECT_HOST:8000`)에 넘어간다. 관리자 server(029)도 같은 앱에 닿는다.

### 3.2 창 상한 — server
창 = `end − start`(두 기본값을 채운 뒤). 상한은 `base` 가 있느냐로만 갈린다(초):

| 조회 | 상한 |
|---|---|
| 전체 | 604800 |
| `base` | 7776000 |

- 창 > 상한이면 400 `invalid_request`. 메시지는 "window exceeds limit" 로 시작해 한도를 사람 말로 적고(예: "전 코인 조회는 한 번에 7일까지"), `detail` 은 `{"limitSec": 604800}` 또는 `{"limitSec": 7776000}`. 창 = 상한은 통과한다.
- 검사 순서: `end ≤ start` 400 → 창 상한 400 → Influx 조회. 거절한 요청은 Influx 를 읽지 않는다. 토큰이 없어 저장소 자체가 없으면 지금처럼 503 이 먼저다(`/history/candles` 와 같은 순서).
- `dom`·`dir` 는 상한을 바꾸지 않는다. 운영 7일(2026-09-21~28) 사건 58,666건 중 역프가 93%·빗썸이 96% 라 방향·거래소 조건으로는 거의 안 줄 때가 있다. 코인 하나는 다르다 — 가장 많은 코인도 7일 1,471건(전체의 2.5%)이다.
- 기본 창(`start` 없음)은 상한과 같아 늘 통과한다. `start` 만 주고 `end` 를 빼면 `end` 가 지금+1초라 `start = 지금 − 7일` 은 1초 넘어 400 이다 — 상한에 딱 맞춘 창은 `end` 를 함께 준다(웹은 늘 준다).
- 왜 7일: 기록 탭 기본 기간이자 기본 창이다. 운영 7일 전 코인 응답(58,666건·13.7MB, gzip 1.7MB, 운영 ≈17초)이 곧 요청 하나의 최악이 되고, 하루 사건 수가 늘지 않는 한 더 커지지 않는다. 1달은 지금도 33초이고, 30일이 사건으로 다 차는 10월 초에는 두 배 넘게 되어 nginx 읽기 제한(기본 60초)에 닿는다(추정). 파이썬 메모리도 사건 수에 비례한다(7일 치를 읽는 데 +97MB, 2026-09-28 로컬 실측) — 같은 속도면 3달 치는 1GB 를 넘는다(추정).
- 왜 90일(`base`): 7일에 사건이 가장 많은 코인(GRT 역프 1,471건)을 90일로 늘려도 약 1.9만 건·4.4MB 로 전 코인 7일의 3분의 1이다. 차트 첫 화면이 음영용으로 부르는 범위는 1h 봉까지 최대 30일, 4h 봉 120일, 1d 봉 720일이다 — 1h 봉까지는 그대로 들어오고 4h·1d 봉은 최근 90일만 칠한다(§3.3).
- 상한 두 값은 코드 상수다(env 아님). 웹이 같은 값을 알아야 해서(기간 버튼·음영 자르기) 서버만 바꾸면 화면이 400 을 받는다 — 바꾸려면 이 스펙과 웹을 같이 고친다.
- 이 라우터가 뜨는 곳(수집기 역할, 로컬 단일 프로세스)은 모두 같은 규칙이다. 공개와 관리자(029)도 같다 — 긴 기간 분석은 이 API 가 아니라 박스 안에서 Influx 를 직접 읽는다.
- 랜딩(022 — `premium_event` 7일을 Influx 에서 직접)과 기동 복원(013)은 이 HTTP 경로를 거치지 않아 바뀌지 않는다.

### 3.3 web — 기록 탭
- 기간 선택지는 `1시간/4시간/8시간/12시간/24시간/3일/1주`, 기본 1주 그대로. URL `h.per` 에 `30d`·`90d` 가 남은 링크는 허용 값 밖이라 기본값(1주)으로 뜬다(URL 상태의 기존 규칙).
- 표·요약·로그 조회는 창 = 기간 ≤ 1주라 늘 상한 안이다.
- 차트 음영 조회는 `start` 를 "가장 오래된 청크 시작" 과 `end − 90일` 중 늦은 것으로 보낸다. 자르는 것은 요청을 보낼 때다 — 재조회 조건은 지금처럼 청크 시작(과거로 끌기·봉 종류가 바뀔 때만 바뀐다)이어서, 매초 움직이는 `end − 90일` 때문에 재조회가 늘지 않는다.
- 90일보다 앞의 봉(4h·1d 봉, 또는 1h 봉을 90일 가까이 끈 경우)에는 사건 음영이 없다. 사건은 2026-09-07 배포부터 있으므로 2026-12-06 전에는 빠지는 음영이 없다.
- 400 이 오면 지금의 오류 표시(`기록을 불러오지 못했습니다 (HTTP 400)`) 그대로다 — 정상 조작으로는 나오지 않는다.
- 타임라인 축 라벨 규칙(하루 이하 `HH:mm`, 1주 미만 `M/D HH:mm`, 그 이상 `M/D`)은 그대로 둔다. 1주만 `M/D` 에 남는다.

### 3.4 엣지
- `perf/hot-path` 의 60초 공유 캐시가 먼저 들어와 있으면: 400 은 캐시에 담지 않는다(그 작업의 "오류는 담지 않는다" 와 같다). 캐시 키가 몇 개든 키 하나의 크기는 이 상한이 정한다. 그 작업이 웹 창 끝을 60초 경계로 올려도 표는 `start = end − 기간` 이라 창 = 기간이고, 음영은 `end − 90일` 로 자르므로 상한 안이다.
- 하루 사건 수가 크게 늘면(거래소 추가 등) 상한 안의 최악도 비례해 커진다. 7일 전 코인 응답이 운영에서 30MB 를 넘으면 상한을 다시 본다(status.md 빚).
- 028 허용 목록·nginx·배포 계약 테스트는 그대로다.
