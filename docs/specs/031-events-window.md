## 1. 목적
공개 `/api/history/events` 요청 하나가 읽는 기간에 위를 둔다. 지금은 기간 상한이 없어 `start` 를 얼마든지 옛날로 줄 수 있고, 수집기가 그 창의 사건을 전부 Influx 에서 읽어 JSON 으로 만든다 — 2026-09-29 운영 실측 1일 1.8MB·6.8초, 7일 13MB·17초, 30일 28MB·33초. 사건은 하루 6,100~11,200건씩 쌓이고, 이 경로는 평소 1 vCPU 를 80~100% 쓰는 수집 박스(c7g.medium, 2GiB)가 답한다(028). 끝나면 모든 조회는 90일까지만 답하고, 넘으면 Influx 를 읽기 전에 400 이다. 90일은 기록 탭의 가장 긴 기간(3달)이라 화면의 기간 버튼은 그대로다.

## 2. 범위
- 만드는 것: `GET /history/events` 창 상한(`server/app/features/history/`), 차트 음영 조회 범위 자르기(`web/src/features/history/`), 테스트.
- 이 상한이 **하지 못하는 것**: 사건은 배포(2026-09-07) 뒤로만 있어 지금은 90일 창이 사건 전부를 덮는다 — 2026-12-06 까지는 `?start=0` 과 `start = 지금 − 90일` 이 같은 양이고 전 코인 조회는 줄지 않는다. 그 뒤로는 요청 하나의 최악이 "90일 치" 로 멈추지만, 지금 속도면 약 75만 건·175MB 이고 파이썬 메모리는 1GB 를 넘는다(7일 치를 읽는 데 +97MB, 2026-09-28 로컬 실측에서 비례 추정). 요청 하나를 작게 만드는 일은 아래 후속이 맡는다(status.md 빚).
- 하지 않는 것 — 고르지 않은 선택지와 이유(전부 후속 후보):
  - **더 짧은 전 코인 상한(예: 7일).** 요청 하나를 지금 바로 13.7MB 로 묶지만 기록 탭의 1달·3달 버튼이 400 을 받아 버튼을 빼야 한다 — 이번엔 버튼을 두기로 했다(2026-09-29 사람 결정).
  - **요청 속도·동시 요청 제한**(nginx `limit_req`·`limit_conn`). 요청 하나가 운영에서 17~33초라 IP 당 분당 몇 번만 열어 줘도 한 IP 가 코어 하나를 채운다. IP 를 바꿔 가며 부르면 소용이 없고, 같은 공유기 뒤 접속자들은 함께 막힌다. nginx 가 보는 주소는 앞단 caddy 하나라(023) IP 별로 세려면 원 IP 를 넘겨받는 설정이 새로 들고, 027 이 이 경로를 접속 로그에서 빼므로 값을 정할 근거도 없다. 요청 하나의 비용이 작아진 뒤에 본다.
  - **api 역할로 옮기기.** 진행 중 사건이 수집기 메모리에 있어(013 §3.4) api 는 Influx 만으로 진행 중을 다시 판정해야 한다. api 박스(t4g.micro, 1GiB)는 `/ws/spreads`·랜딩을 함께 답하므로 지금 크기의 요청을 옮기면 위험이 그쪽으로 갈 뿐이다. 013·016·021·028 을 함께 고치는 일이라 따로 한다.
  - **코인별 요약 응답·페이지.** 요약(서버가 표의 코인별 수치만 보낸다)은 7일 역프 12.7MB 를 수십 KB 로 줄여 1달·3달을 가볍게 만드는 길이지만, 013 의 응답 계약과 화면 집계를 다시 쓰는 일이라 담당자(hereokay) 결정이다. Influx 는 여전히 창만큼 읽으므로 상한은 그대로 필요하다. 페이지는 표가 전 사건을 모아 집계하므로 받는 총량이 같다.
  - **공유 캐시·숨은 탭 재조회 멈춤·응답 JSON 을 스레드에서 만들기** — 접속자 수에 비례하는 반복 부하는 `perf/hot-path` 작업(미커밋, 013 을 고친다)이 다룬다. 이 스펙과 독립이다(§3.4).
  - **기본 창 변경.** `start` 없으면 `end − 7일`(005·013) 그대로다.
  - 다른 `/history/*`. `premium`·`streaks`·`bulk` 는 공개에서 닫혀 있고(028), `candles` 는 이미 상한이 있다(014).
- 바꾸는 기존 것: 013 §3.4 `/history/events` 에 400 하나(창 상한), 013 §3.5 차트 음영 조회 범위(`start` 를 `end − 90일` 까지만). 기간 버튼·028 허용 목록·nginx 는 그대로다.
- 담당: 013 은 hereokay 담당이라 이 PR 은 013 을 고치지 않는다 — §6 "담당자에게 제안" 을 PR 본문에 적는다(CLAUDE.md §5). 코드(`features/history` server·web)는 이 스펙대로 고친다(028 과 같은 방식). 028 은 이 레포 주인 담당이라 §6 대로 고친다.

## 3. 동작

### 3.1 읽는 계약 (복사)
- 013 §3.4: `GET /history/events?start&end&dom&dir&base` — 전부 선택. `start`·`end` 는 epoch 초 0~4,102,444,800(밖이면 422), `start` 없으면 `end − 7일`(0 미만이면 0), `end` 없으면 지금+1초, `end ≤ start` 면 400 `invalid_request`. `base` 는 `^[A-Za-z0-9]{1,20}$` 이고 대문자로 바꾼다. 구간 판정 `start ≤ start_ts < end`. 응답 = Influx 의 닫힌 사건 + 수집기 메모리의 진행 중 사건. Influx 가 없거나 닿지 않으면 503 `storage_unavailable`.
- 005: 오류 본문 `{"error":{"code","message","detail"}}`, HTTP 키 camelCase.
- 014 §3.6: `/history/candles` 는 `end − start` 가 상한을 넘으면 400 `invalid_request`, 메시지 "window exceeds limit…", `detail` `{"limitSec": 상한}` 이다. 이 스펙이 같은 모양을 쓴다.
- 013 §3.5·014 §3.7(web): 기록 탭은 표·요약·로그용으로 `start = 지금 − 기간`, `end = 지금`, `dir` 을 늘 붙여 부르고, 국내 거래소를 고르면 `dom` 도 붙인다. 기간은 `1시간/4시간/8시간/12시간/24시간/3일/1주/1달/3달`(기본 1주, 1달 = 30일·3달 = 90일). 차트 음영용으로는 선택 심볼 `base` 와 "가장 오래된 청크 시작 ~ 지금" 을 따로 부른다 — 청크 = 360창(1m 6시간·5m 30시간·1h 15일·4h 60일·1d 360일), 과거로 끌면 청크를 더 붙인다. 둘 다 60초마다 다시 부른다.
- 028: 공개 `/api/history/events` 는 정확 일치로 수집기(`COLLECT_HOST:8000`)에 넘어간다. 관리자 server(029)도 같은 앱에 닿는다.

### 3.2 창 상한 — server
- 창 = `end − start`(두 기본값을 채운 뒤). 상한은 **7,776,000초(90일)** 하나다 — `base`·`dom`·`dir` 와 무관하다.
- 창 > 상한이면 400 `invalid_request`. 메시지는 "window exceeds limit" 로 시작해 한도를 사람 말로 적고(예: "한 번에 90일까지"), `detail` 은 `{"limitSec": 7776000}`. 창 = 상한은 통과한다 — 기록 탭 3달 버튼의 창이 정확히 상한이다.
- 검사 순서: `end ≤ start` 400 → 창 상한 400 → Influx 조회. 거절한 요청은 Influx 를 읽지 않는다. 토큰이 없어 저장소 자체가 없으면 지금처럼 503 이 먼저다(`/history/candles` 와 같은 순서).
- 기본 창(`start` 없음, 7일)은 늘 통과한다. `start` 만 주고 `end` 를 빼면 `end` 가 지금+1초라 `start = 지금 − 90일` 은 1초 넘어 400 이다 — 상한에 딱 맞춘 창은 `end` 를 함께 준다(웹은 늘 준다).
- 왜 90일: 기록 탭의 가장 긴 기간과 같아 화면을 바꾸지 않는 가장 작은 상한이다. `start` 를 옛날로 끝없이 미는 요청(예: `?start=0`)이 기록이 쌓일수록 커지는 길을 닫는다.
- 상한은 코드 상수다(env 아님). 웹이 같은 값을 알아야 해서(3달 버튼·음영 자르기) 서버만 바꾸면 화면이 400 을 받는다 — 바꾸려면 이 스펙과 웹을 같이 고친다.
- 이 라우터가 뜨는 곳(수집기 역할, 로컬 단일 프로세스)은 모두 같은 규칙이다. 공개와 관리자(029)도 같다 — 더 긴 기간 분석은 이 API 가 아니라 박스 안에서 Influx 를 직접 읽는다.
- 랜딩(022 — `premium_event` 7일을 Influx 에서 직접)과 기동 복원(013)은 이 HTTP 경로를 거치지 않아 바뀌지 않는다.

### 3.3 web — 기록 탭
- 기간 버튼은 그대로다. 표·요약·로그 조회는 창 = 기간 ≤ 90일이라 늘 상한 안이다.
- 차트 음영 조회는 `start` 를 "가장 오래된 청크 시작" 과 `end − 90일` 중 늦은 것으로 보낸다. 차트 첫 화면이 음영용으로 부르는 범위는 1h 봉까지 최대 30일, 4h 봉 120일, 1d 봉 720일이라 4h·1d 봉과 과거로 많이 끈 1h 봉에서만 잘린다. 자르는 것은 요청을 보낼 때다 — 재조회 조건은 지금처럼 청크 시작(과거로 끌기·봉 종류가 바뀔 때만 바뀐다)이어서, 매초 움직이는 `end − 90일` 때문에 재조회가 늘지 않는다.
- 90일보다 앞의 봉에는 사건 음영이 없다. 사건은 2026-09-07 배포부터 있으므로 2026-12-06 전에는 빠지는 음영이 없다.
- 400 이 오면 지금의 오류 표시(`기록을 불러오지 못했습니다 (HTTP 400)`) 그대로다 — 정상 조작으로는 나오지 않는다.

### 3.4 엣지
- 1달·3달 조회는 창이 사건으로 차면서 느려진다. 1달은 지금 33초이고 30일이 다 차는 10월 초에는 두 배 넘게 되어 nginx 읽기 제한(기본 60초)에 닿는다(추정) — 그 뒤 1달·3달 버튼은 504 를 받을 수 있다. 3달 치가 차면 Influx 쿼리 메모리 상한(256MB)에도 가까워진다(추정 — 7일 조회가 16.5MB). 이 스펙은 이것을 막지 않는다. 막는 길은 코인별 요약 응답이고, 그 전까지 느려지면 사람이 7일 상한·버튼 삭제로 다시 정한다(status.md 빚).
- `perf/hot-path` 의 60초 공유 캐시가 먼저 들어와 있으면: 400 은 캐시에 담지 않는다(그 작업의 "오류는 담지 않는다" 와 같다). 그 작업이 웹 창 끝을 60초 경계로 올려도 표는 `start = end − 기간` 이라 창 = 기간이고, 음영은 `end − 90일` 로 자르므로 상한 안이다.
- 028 허용 목록·nginx·배포 계약 테스트는 그대로다.
