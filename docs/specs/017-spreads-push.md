## 1. 목적
스프레드 표가 1초 폴링이 아니라 **WebSocket 푸시**로 온다. 표는 수집 프로세스가 매초 만들고, `api` 컨테이너가 **바뀐 행만** 접속자 전원에게 같은 바이트로 뿌린다. 접속자가 늘어도 수집 프로세스의 일은 늘지 않고, 브라우저는 안 바뀐 행을 매초 다시 받지 않는다(실측 2026-09-14: 폴링 1명당 54KB/s·요청의 50%, 페이지 이동 시 499).

한계를 먼저 적는다. 김프는 모든 행이 환율(`rate`)로 나뉘어 계산되므로 **환율이 한 틱 움직이면 약 490행 전부가 바뀐 행**이 되어 전체 크기 프레임이 나간다. `spark` 도 벽시계 1분 버킷이라 **매분 롤오버 때 전 행이 바뀐다.** 그래서 절감은 "환율이 조용한 초"에만 생기고, 그 비율은 §4 의 실측으로 확인한다 — 실측 전에는 절감 숫자를 약속하지 않는다.

## 2. 범위
- 만드는 것: 수집 프로세스의 표 게시(Redis), `api` 의 `/ws/spreads`, FE 의 WebSocket 구독(폴링 대체), nginx·vite 의 WebSocket 프록시, 체결 규모 집합 교체(`$100·$1k·$2k·$5k`, 기본 `$100`)
- 하지 않는 것: `GET /spreads` 제거(진단·curl 용으로 남긴다), 분석 엔드포인트·`/health/collect` 의 푸시화, 호가 원본 공유, 인증, 접속자 수 집계 화면, 티커 기반 김프의 브라우저 계산, 페이로드 압축(로컬 도커망이라 이득이 없고 수집 CPU 만 쓴다 — HTTP 는 기존 GZip 미들웨어가 하고 WebSocket 은 압축 없이 보낸다)
- 바꾸는 기존 것: 016 §3.1 — `api` 역할이 Redis 에 **구독 목적으로만** 연결하고(스트림 `ticks` 는 안 읽는다) 백그라운드 태스크를 **구독 태스크 하나** 가진다, 서빙 경로에 `/ws/spreads` 추가. 003 §3.4 — FE 1초 폴링 절을 이 스펙의 구독으로 교체. 007 — nginx 에 WebSocket 위치 추가.

## 3. 동작

### 3.1 수집 프로세스 — 표 게시
- 규모 집합은 서버 상수 **`100, 1000, 2000, 5000`**(USD), 기본은 첫 값 `100` — FE 선택지·서버 `GET /spreads` 기본값과 같다(003 §3.2-0·§3.5 의 값을 이 집합으로 바꾼다. 범위 규칙 `1 ≤ notional ≤ 10_000_000` 은 유지).
- **원하는 규모만 만든다.** 서빙 프로세스(3.2)는 접속자가 1명 이상인 규모마다 Redis 키 `spreads:want:<N>` 을 **5초마다 `SET … EX 15`** 로 갱신한다. 수집 프로세스는 이 키들을 **5초마다** 읽어 메모리에 "원하는 규모 집합"으로 들고, 틱 루프는 그 메모리 값만 본다(틱 안에서 Redis 를 부르지 않는다 — 003 §2 의 "표 계산은 await 없음" 유지). 아무도 안 보면 표를 하나도 안 만든다 — 접속자 0명일 때 수집 프로세스의 일이 오늘과 같아야 한다. 새 규모를 처음 고른 접속자는 키 갱신 → 수집 반영 → 첫 게시까지 **최대 10초** 기다린다(그동안 `waiting`, 3.3).
- 틱 루프가 틱을 만든 직후, 같은 회차에서 원하는 규모 각각의 표를 003 §3 규칙 그대로 만든다(`GET /spreads?notional=N` 응답과 **같은 JSON**, camelCase, `fetchedAt` 은 만든 시각). 만든 표는 틱 인계(009)와 같은 방식으로 큐에 넣고 별도 태스크가 Redis 로 보낸다 — 게시 실패가 틱을 막지 않는다.
- 게시: 규모마다 `PUBLISH spreads:<N> <JSON>` + `SET spreads:latest:<N> <JSON> EX 10`. 채널은 실시간, 키는 늦게 붙은 구독자(api 재기동·그 규모 첫 접속자)의 첫 표다. TTL 10초 — 수집이 멈추면 키도 사라져 "없음"이 곧 신호다.
- Redis 불달이면 이 회차 게시는 건너뛰고 경고 1줄, 같은 원인은 60초에 1줄(009 의 인계 실패 로그와 같은 톤).
- 표 생성이 한 회차 **300ms** 를 넘으면 경고 1줄. 규모별 표 생성 비용은 접속자 수와 무관하고 원하는 규모 수(최대 4)에만 비례한다. 300ms 는 실측(§4) 뒤 실행 세션이 고쳐도 된다.

### 3.2 서빙 프로세스 — 구독·diff·브로드캐스트
`api` 역할이 한다. 로컬 개발은 프로세스 하나(`collector` 역할)라 그 프로세스가 자기 게시를 자기 구독해 같은 일을 한다. 배포의 `server` 컨테이너도 `collector` 역할이라 같은 코드가 뜨지만, nginx 가 `api` 로만 보내므로 접속자가 없고 아래 규칙대로 아무 일도 안 한다.
- 기동 시 Redis 에 연결해 `spreads:*` 4채널을 구독한다. 이 구독 연결은 오래 살아 있으므로 끊기면 **1→2→4→…→30초** 백오프로 다시 연결한다(기존 Redis 클라이언트는 명령마다 lazy 연결이라 백오프가 없다 — 이 스펙이 새로 만드는 동작이다). Redis 불달이어도 `/ws/spreads` 는 열리되 표가 없다.
- **접속자가 1명 이상인 규모만** 상태를 든다: 규모마다 **직전 표 1장**. 어떤 규모의 첫 접속자가 생기면 `spreads:latest:<N>` 을 읽어 시작 표로 삼고(없으면 `waiting`), 접속자가 0명이 되면 그 규모의 직전 표를 버린다. 접속자 0명인 규모의 채널 메시지는 **파싱하지 않고 버린다** — 배포의 `server` 컨테이너와 아무도 안 보는 규모에 비용이 없게.
- 새 표가 오면 규모당 1회 diff 를 만들고, 그 규모를 고른 접속자 전원에게 **같은 직렬화 결과**를 보낸다. 접속자별 직렬화는 없다.
- diff 규칙: 행의 키는 `(sym, dom, fx)`. 행이 **바뀜** = `age` 를 제외한 어느 필드라도 직전과 다름(`spark` 배열 포함). `age` 만 다른 행은 안 보낸다 — 매초 모든 행의 `age` 가 늘어 diff 가 무의미해지기 때문이고, 브라우저가 스스로 키운다(3.4). 직전에 있었는데 사라진 키는 `removed` 에 넣는다. `status` 가 바뀌면(ok→stale 등) 그 행은 바뀐 행이라 현재 `age` 와 함께 나간다. 환율이 바뀐 초와 매분 롤오버 초에는 사실상 전 행이 실린다(§1) — 그래도 delta 로 보낸다, 특별 취급 없음.
- **하트비트**: 어느 연결에든 **1초 넘게 아무것도 안 보냈으면** `{"type":"heartbeat"}` 를 보낸다. 표가 매초 오면 delta 가 그 자리를 채우고, 수집이 멈추면 heartbeat 만 간다. 브라우저 JavaScript 는 WebSocket ping/pong 프레임을 볼 수 없으므로 살아 있음은 **메시지로만** 알린다 — 따로 ping 프레임을 보내지 않는다. nginx 유휴 타임아웃(기본 60초)도 이 1초 메시지로 넘긴다.
- **느린 클라이언트**: 연결마다 보내기 대기열을 따로 두고 서로 기다리지 않는다. 대기열에 **5개**(약 5초분) 이상 쌓이면 그 연결을 코드 1008 로 닫는다. 한 명이 전원을 늦추지 않게. (전송 시간으로 자르지 않는 이유: 순차 전송이면 한 명이 제한 시간만큼 전원을 막는다.)

### 3.3 외부 계약 — `GET /ws/spreads` (WebSocket 업그레이드)
- 인증 없음(`GET /spreads` 와 같다). 서브프로토콜 없음. 메시지는 텍스트 JSON.
- 클라이언트 → 서버:
  - `{"type":"subscribe","notional":100}` — 규모 선택·변경. 4개 값 외는 `{"type":"error","code":"bad_notional","message":…}` 1회 후 직전 규모 유지(처음이면 아무것도 안 보낸다). 연결 후 **30초** 안에 유효한 subscribe 가 없으면 1008 로 닫는다 — 잘못된 subscribe 는 이 타이머를 리셋하지 않는다.
- 서버 → 클라이언트:
  - `{"type":"snapshot", "notional":100, "rate":…, "rows":[…17키 행 전부…], "warnings":[…], "dataReceivedAt":…, "fetchedAt":…}` — subscribe 직후·규모 변경 직후, 그리고 `waiting` 뒤 첫 표가 왔을 때. 행은 003 §3.2 그대로.
  - `{"type":"delta", "notional":100, "rate":…, "rows":[바뀐 행 전부 17키], "removed":["BTC|upbit|binance", …], "warnings":[…], "dataReceivedAt":…, "fetchedAt":…}` — 새 표마다. `removed` 의 원소는 `sym|dom|fx`. 바뀐 행이 없으면 `rows: []` 로 보낸다(`rate`·`warnings`·시각은 갱신돼야 하므로).
  - `{"type":"heartbeat"}` — 1초 넘게 보낸 게 없을 때(3.2).
  - `{"type":"waiting"}` — subscribe 했는데 그 규모의 표가 아직 없을 때(수집 기동 직후·Redis 불달·그 규모 첫 접속). 첫 표가 오면 snapshot.
- 닫기 코드: 1008 = 느린 클라이언트·subscribe 없음, 1001 = 서버 종료. 클라이언트는 어느 코드든 재연결한다.

### 3.4 FE — 구독
- 셸이 공유 피드를 만든 직후 **연결 하나**를 연다(폴링이 살던 자리). 주소는 `API_BASE` 가 상대경로(`/api`)이므로 **페이지 origin 기준 절대 URL** 로 만든 뒤 스킴만 `http→ws`·`https→wss` 로 바꾼다 — 결과는 `ws(s)://<host>/api/ws/spreads`. 규모 세그먼트 값이 바뀌면 같은 연결에 subscribe 를 다시 보낸다(재연결 아님).
- `snapshot` → 행의 `dom`/`fx` 를 표시명으로 바꿔 공유 피드에 통째 교체(003 과 같다). `delta` → 키로 행을 갱신·추가, `removed` 를 삭제, `rate`·`warnings`·`dataReceivedAt` 갱신. **`notional` 이 지금 고른 규모와 다른 snapshot·delta 는 버린다** — 규모를 바꾼 직후 옛 규모 delta 가 도착할 수 있다. 안 온 행은 그대로 두고 **`age` 는 셸의 1.5초 tick 이 계속 키운다**(002 규칙 그대로) — 그래서 서버가 안 보낸 행이 저절로 stale 로 간다. `heartbeat`·`waiting` 은 표를 건드리지 않는다.
- **무응답 감지**: 어떤 종류든 서버 메시지가 **10초** 동안 없으면 연결을 닫고 재연결한다. 반쯤 죽은 연결(절전·망 전환)은 이것으로만 잡힌다.
- 끊기면 1→2→4→…→30초 백오프로 재연결하고, 재연결 시 subscribe 부터 다시 한다(snapshot 이 온다). 재연결 대기 중에도 직전 표를 지우지 않는다.
- **폴링 fallback**: 연결 시도 후 **5초** 안에 서버 메시지가 하나도 없으면 `GET /spreads?notional=N` 을 **5초마다** 폴링하고, snapshot 이 오는 순간 폴링을 끝낸다. `waiting` 을 받았으면 폴링하지 않는다 — 표가 없는 건 서버도 같아서 `GET` 도 404 다. WebSocket 을 막는 망에서도 표는 뜨되 1초 갱신은 포기한다.
- 탭을 옮겨도 연결은 유지한다(헤더 KPI 의 환율이 이 연결에서 온다). 페이지를 닫으면 브라우저가 연결을 닫는다 — 499 는 생기지 않는다.
- `/health/collect` 5초 폴링(011)은 그대로.

### 3.5 프록시
- nginx: `location /api/ws/` (앞부분 일치) 를 `proxy_pass http://api:8000/ws/;` 로 넘긴다 — 접두 위치라 016 의 정규식 rewrite 는 필요 없다. `proxy_http_version 1.1` + `Upgrade`·`Connection "upgrade"` 헤더, 기존 프록시 헤더 4개 동일. `proxy_read_timeout` 은 **손대지 않는다**(기본 60초 — 1초 하트비트가 있어 안 끊긴다, 016 과 같은 입장).
- vite dev 프록시: `/api` 항목에 `ws: true`.

### 3.6 엣지
- 수집 프로세스 재시작: 채널이 잠시 조용 → api 는 heartbeat 만 → 브라우저 표가 stale 로 감 → 첫 표가 오면 delta(대부분 행이 바뀜). snapshot 을 다시 보내진 않는다.
- api 재시작: 접속자 전원 끊김 → 재연결 → 첫 subscribe 가 `spreads:latest` 를 읽어 즉시 snapshot(키가 만료됐으면 `waiting`).
- 수집 프로세스가 `spreads:want:*` 를 읽는 사이 접속자가 사라지면 키가 15초 뒤 만료되고 다음 읽기에서 그 규모 생성이 멈춘다 — 최대 20초 더 만든다, 문제 없음.
- 같은 초에 표가 2장 오면(재게시) 나중 것 기준으로 diff.

## 4. 검증
- **실측(구현 전, EC2)**: 연속 두 `GET /spreads?notional=100` 응답을 1초 간격으로 5분간 비교해 (1) `age` 제외 바뀐 행 비율의 중앙값, (2) `rate` 가 바뀐 초의 비율, (3) 표 1장 생성 시간을 잰다. 결과를 §5 에 기록한다. (1) 이 절반을 넘거나 (3)×4 가 300ms 를 넘으면 실행 세션은 멈추고 사람과 3.1 의 상수를 다시 정한다.
- 수집: 원하는 규모 키가 없으면 표를 만들지 않는다 / 키가 있는 규모만 채널·키가 쓰인다 / 채널 페이로드는 **같은 틱 안에서** 만든 `GET /spreads?notional=N` 응답과 JSON 이 같다(시각 필드 `fetchedAt`·`dataReceivedAt`·`age` 는 같은 틱에서 비교)
- 수집: Redis 불달이면 게시만 건너뛰고 틱 인계는 계속
- diff: `age` 만 바뀐 행은 안 실린다 / `status` 가 바뀐 행은 실린다 / 사라진 행은 `removed` / 바뀐 행 0개여도 delta 1개
- diff: 접속자 3명(같은 규모)에게 간 바이트가 동일하다 / 다른 규모는 다른 delta / 접속자 0명인 규모의 채널 메시지는 파싱되지 않는다
- `/ws/spreads`: subscribe → snapshot, 규모 변경 → snapshot, 잘못된 규모 → error 후 유지, 30초 무응답 → 1008(잘못된 subscribe 는 리셋 안 함), 표 없음 → waiting → 첫 표에 snapshot, 1초 무전송 → heartbeat
- 서빙: 어떤 규모의 첫 접속자가 `spreads:latest` 로 즉시 snapshot 을 받는다 / 접속자 있는 규모의 `spreads:want:<N>` 이 5초마다 갱신된다
- 느린 클라이언트 대기열 5개 → 1008, 다른 접속자는 지연 없음

- 수동: 브라우저 DevTools 에서 20초 관찰 시 `/spreads` 요청 0건, WS 프레임 초당 1개(delta 또는 heartbeat). 탭 이동 후에도 프레임 계속. `docker compose stop server` 후 heartbeat 만 오고 표가 stale 로 가고, 재기동 후 복구
