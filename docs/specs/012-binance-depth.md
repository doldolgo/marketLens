# 012 — binance-depth

상태: DONE | 의존: 001(collect — 사이클·커넥터 계약·Row), 011(health — 실패 분류·구간 추적), 007(deploy — compose·lifespan)

> 이 문서는 이 기능이 **지금 어떻게 동작해야 하는지**를 적는다. 동작이 바뀌면 이 문서를 직접 고치고, 같은 PR 에서 코드·테스트도 맞춘다(CLAUDE.md §4·§6). 사람이 끝까지 읽는 문서다 — 코드를 산문으로 옮기지 않는다.

## 1. 목적
바이낸스 호가를 **최대 20단계**까지 들고 있게 한다. 지금 메모리에 있는 해외 호가는 최우선 1단계뿐이라 호가를 걷는 계산(003 의 슬리피지, 004 의 `/slippage`·`/arbitrage`)이 해외 쪽에서 성립하지 않는다.

REST 로는 불가능하다. `GET /api/v3/depth` 는 심볼당 1회이고 `limit ≤ 100` 이 weight 5 다. 대상 ~300 종목이면 사이클당 1,500 weight, 1초 주기로 분당 90,000 — IP 한도 6,000/분의 15배다. 그래서 **WebSocket 깊이 스트림**을 REST 사이클과 나란히 돌린다.

## 2. 범위
- 만드는 것: `core/connectors/` 의 바이낸스 깊이 스트림 클라이언트(연결·구독·디코딩)와 **깊이 캐시**(심볼 → 호가 + 수신 시각), 앱 기동이 관리하는 샤드 태스크, 스트림 정체를 수집 실패로 승격하는 **watchdog**, 라이브러리 `websockets`, 테스트.
- 바꾸는 기존 것: ① 001 — `Row` 에 깊이 3필드 추가, 바이낸스 수집 3단계가 캐시를 읽어 싣는다, §3.5 바이낸스 절에 스트림 설명, §4 의 "사이클 2회·18회" 문구. ② 011 — 실패 종류에 `stale_stream` 추가, §3.2 분류 표에 행 추가. ③ 011·status.md 가 "후속 012" 로 가리키던 백오프·서킷브레이커를 **013** 으로 재지정(문구만, 코드 영향 없음).
- 하지 않는 것: REST 호출 대체(§3.4 이유). 국내 거래소 스트림(업비트 30·빗썸 15단계를 이미 REST 로 받는다). diff depth 와 로컬 북 재구성(§3.2 이유). 깊이를 쓰는 계산 자체(003·004 몫 — 이 스펙은 데이터만 채운다). HTTP 응답 계약 변경 — **012 는 API 를 한 글자도 바꾸지 않는다.**

## 3. 동작

### 3.1 읽는 계약 (복사)
- 001: 수집 사이클은 1초 주기이고, 커넥터는 `fetch_rows(client)` 로 `Row` 목록을 돌려준다. 거래소 quirk 는 각 커넥터 안에서만 흡수한다. 사이클 끝에 LiveStore 를 거래소 단위로 통째 교체한다. 바이낸스 대상은 **국내 KRW 마켓과의 교집합**이다.
- 001: `Row.asks`/`Row.bids` 는 `[price, size]` 목록이고 국내는 누적 10억 KRW 까지, 바이낸스는 1단계다.
- 011: 커넥터가 자기 규칙으로 실패를 분류해 `ExchangeError(kind=…)` 로 던지고, collector 가 그 예외를 받아 구간 추적기에 기록한다. **예외가 안 나면 성공으로 기록된다.**

### 3.2 스트림 선택
- 엔드포인트 `wss://data-stream.binance.vision/stream`(시세 전용 호스트). 스트림은 심볼마다 **`<symbol>@depth20`** — 상위 20단계를 1000ms 마다 통째로 보내는 **자기완결 스냅샷**이다.
- 자기완결이라는 점이 이 선택의 이유다. 끊겼다 붙어도 다음 메시지 하나로 책이 완전히 복구되므로 **REST 재동기화·시퀀스 관리·갭 감지가 전부 필요 없다.**
- `<symbol>@depth`(diff) 는 쓰지 않는다. 심볼마다 `depth?limit=5000`(weight 250)으로 로컬 북을 만들고 U/u 시퀀스를 이어 붙여야 하는데, 300종목 초기화만 75,000 weight 라 §1 의 한도 계산에 다시 걸린다.
- 단계 수 20 은 partial depth 가 허용하는 최대값이다(5·10·20). 갱신 주기는 1000ms — 수집이 1초 주기이고 LiveStore 가 1초마다 교체되므로 100ms 는 9/10 을 버린다. 둘 다 코드 상수로 두어 내릴 여지를 남긴다(1000ms 는 접미사가 없고, 내리면 스트림 이름이 `<symbol>@depth20@100ms` 가 된다).
- 깊이가 아닌 프레임(구독 응답 `{"result":null,"id":1}`, 깨진 JSON, 모양이 다른 메시지)은 조용히 버리고 소켓은 유지한다. 이런 프레임은 §3.6 의 "수신" 으로도 세지 않는다 — 세면 소켓이 응답만 하고 깊이는 멈춘 상태를 정상으로 본다.
- 대역폭 감: 메시지 ~1.3KB × 300종목 × 1/s ≈ 400KB/s. EC2 인바운드는 과금 대상이 아니다.

### 3.3 구독 대상과 샤딩
- 대상 = **LiveStore 의 바이낸스 스냅샷에 있는 base 집합**. 이미 국내 교집합이 적용된 결과라 별도 목록을 관리하지 않고 상장·상폐를 자동으로 따라간다. 기동 직후 첫 REST 사이클 전에는 비어 있어 구독이 없다.
- 대상 재조정은 **60초** 주기. 새 심볼은 SUBSCRIBE, 사라진 심볼은 UNSUBSCRIBE 하고 캐시에서 지운다. 소켓은 기동 즉시 붙지만 그때 메모리가 비어 있으므로 **실제 첫 구독은 기동 후 첫 재조정(최대 60초)** 에 일어난다. 그 사이 깊이는 빈 목록이고 소비자는 §3.5 규칙대로 1단계로 돈다.
- **3 샤드**로 나눈다. 300 스트림은 연결당 한도 1,024 안에 들어가 1연결로도 되지만, 한 소켓이 죽을 때 전 종목 깊이가 동시에 사라지는 것을 막는 게 목적이다. 3샤드면 한 번에 1/3 만 잃는다. 24시간 강제 종료도 샤드마다 다른 시각에 걸린다.
- 샤드 배정은 **심볼 문자열의 안정 해시 % 3**. 상장·상폐가 나머지 심볼의 배정을 흔들지 않는다.
- 구독은 URL 이 아니라 **연결 후 SUBSCRIBE 메시지**로 한다(300종목을 `?streams=` 에 넣으면 URL 이 ~7KB 라 414 위험). 한 메시지의 `params` 는 ≤100 스트림. 바이낸스 한도는 연결당 수신 제어 메시지 **5개/초**라 샤드당 최초 2메시지면 여유가 있다.
- 연결 시도는 IP 당 5분에 300회 한도다. 재연결은 지수 백오프(1·2·4·8초, 상한 30초)로 하고, **구독까지 성공하면 1초로 되돌린다**. 실패 1회 = 경고 로그 1줄.

### 3.4 깊이 캐시와 커넥터
```
[WS 3샤드 태스크] ──▶ 깊이 캐시 (심볼 → {asks, bids, at})
                              │  동기 dict 읽기 — await 없음
                              ▼
[REST 2회/1초] ──▶ 바이낸스 커넥터 ──▶ Row(asks, bids, depth_asks, depth_bids, depth_at)
                                              ▼
                                  001 수집 사이클 그대로 ──▶ LiveStore
```
- 깊이 캐시는 프로세스 메모리의 평범한 dict 다. WS 태스크가 쓰고 커넥터가 읽는다. 같은 이벤트 루프 안이고 읽기에 `await` 가 없어 락이 필요 없다 — **이 성질은 003 이 의존한다(호가를 걷는 계산이 동기 함수여야 하는 이유).**
- 캐시 키는 **바이낸스 원본 심볼 대문자**(`BTCUSDT`)다. 스트림 이름(`btcusdt@depth20`)과 `Row.native_symbol` 이 같은 값으로 이어져 base↔symbol 변환이 한 군데에도 없다.
- 캐시는 커넥터에 **주입**한다. `fetch_rows(client)` 시그니처와 커넥터 공통 인터페이스는 불변이라 collector 는 이 스펙을 모른다. 테스트는 가짜 캐시를 넣는다. 커넥터가 캐시에서 읽는 것은 심볼 조회와 정체 여부 둘뿐이다.
- 샤드 태스크의 기동·종료는 앱 lifespan 이 맡는다(010 snapshot 루프와 같은 자리·같은 취소 패턴). 종료는 취소 후 대기, 그 다음 소켓 close. **소켓 3개는 동시에 닫고 합계 2초를 넘기지 않는다** — 상대가 close 프레임을 안 돌려주면 하나당 최대 20초를 기다려 배포의 `docker stop`(10초)보다 종료가 길어진다. 남은 TCP 는 프로세스가 끝날 때 OS 가 정리한다.
- 깊이 항목의 **TTL 은 10초**다. 그보다 낡으면 없는 것으로 친다.
- **REST 2회 호출은 그대로 둔다.** 최우선 호가와 마지막 체결가는 사이클 시각의 값이어야 하는데, partial depth 는 북이 안 움직이면 메시지가 오지 않아 조용한 알트가 몇 분 낡을 수 있다. 그리고 스트림이 죽어도 바이낸스 행이 통째로 사라지지 않는다. weight 8/사이클 = 분당 480 으로 한도의 8% 라 아낄 이유가 없다.

### 3.5 `Row` 의 깊이 필드
- `depth_asks`·`depth_bids` — 최대 20단계, `[price, size]`. 스트림이 없거나 TTL 을 넘겼으면 **빈 목록**. 국내 거래소는 항상 빈 목록이다.
- `depth_at` — 그 깊이를 받은 시각(epoch ms). 없으면 null.
- 저장 상한: 국내가 누적 10억 KRW 인 것과 대칭으로 **누적 1,000,000 USDT 에 도달한 단계까지** 자른다(최소 1단계는 남긴다). 003 이 제공하는 최대 체결 규모 $500k 의 2배 여유다. 자르는 시점은 **커넥터가 `Row` 를 만들 때**다 — 캐시에는 받은 그대로 두어야 상한을 바꿔도 다음 메시지를 기다리지 않는다.
- 소비자 규칙(001 §3.3 에 명시): **호가를 걷는 계산은 `depth_*` 가 비어 있지 않으면 그것을, 비면 `asks`/`bids` 를 쓴다.** 국내는 `asks`/`bids` 가 이미 깊으므로 이 규칙 하나로 세 거래소가 균일하게 처리된다.
- `asks`/`bids` 자체는 건드리지 않는다. REST 최우선 호가와 WS 북을 섞으면 교차(crossed) 북이 나오고, 003(DONE) 의 fwd/rev 정의가 바뀐다. 분리해 두면 이 스펙은 HTTP 계약을 바꾸지 않는다.

### 3.6 스트림 정체 감지 (watchdog)
011 의 구간 추적은 **커넥터가 예외를 던질 때만** 동작한다. 소켓이 조용히 멈추면 예외가 없어 `/health/collect` 가 계속 초록인 채로 깊이만 얼어붙는다. 그래서 정체를 명시적으로 실패로 승격한다.

- 새 실패 종류 **`stale_stream`** 을 011 의 종류 목록에 추가한다.
- 판정 단위는 **샤드 하나**다. 구독 중인 심볼이 있는 샤드가 **30초 동안 메시지를 받지 못하면**, 다른 샤드가 멀쩡해도 그 사이클의 바이낸스 수집이 `ExchangeError(kind="stale_stream")` 을 던진다. 샤드 하나가 죽으면 그 샤드의 심볼(전체의 약 1/3)만 TTL 10초 뒤 조용히 1단계로 되돌아가는데, 전체 기준으로 판정하면 그 열화가 어디에도 드러나지 않는다. message 에 정체된 샤드 번호와 그 샤드의 구독 수를 담는다. 커넥터가 던지므로 011 의 기존 경로(collector → 구간 추적기 → `collect_fail`)를 그대로 탄다. 예외는 `exchange_api_error` 이고 `url`·`status_code` 는 null 이다.
- 무수신을 세는 기준 시각은 **그 샤드의** 마지막 깊이 메시지 수신 시각, 아직 한 번도 못 받았으면 그 샤드가 구독을 시작한 시각이다. 구독이 0개인 샤드는 판정 대상이 아니다(기동 직후 첫 재조정 전이 그렇다).
- 예외는 REST 호출 **뒤에** 던진다. 호출 수가 줄면 안 되고(§4 회귀), 사이클 시각의 최우선 호가는 정상적으로 받아둬야 다음 성공 사이클이 이어진다.
- 이때도 REST 결과는 유효하므로 **행이 사라지면 안 된다** — 예외는 사이클을 실패로 기록하되, 001 의 "실패한 거래소는 직전 스냅샷을 유지한다" 규칙에 따라 표는 계속 뜬다.
- 정체가 풀리면 다음 사이클이 성공으로 기록돼 구간이 닫힌다. 여러 샤드가 동시에 정체면 구간은 여전히 1건이다 — 011 의 기록 단위가 거래소별 연속 실패 구간이기 때문이다. 구간이 1건이니 message 가 가리키는 샤드도 하나다: **가장 오래 조용한 샤드**를 고르고, 무수신 시간이 같으면 번호가 작은 쪽이다.

### 3.7 장애 격리
- 스트림이 한 번도 못 붙어도 앱은 뜬다. 경고 로그 1줄, 샤드는 백오프로 재시도, `depth_*` 는 빈 목록이라 소비자는 §3.5 규칙대로 1단계로 되돌아간다.
- 컨테이너 재생성마다 북이 사라지지만 partial depth 라 다음 메시지 하나로 복구된다. 별도 재동기화 경로가 없는 이유다.
- 라이브러리 `websockets` 를 `pyproject.toml` 에 명시 추가한다(지금은 `uvicorn[standard]` 를 통해 전이 의존이라 CI·Dockerfile 두 설치 경로 모두 보장되지 않는다).

## 4. 검증
네트워크 없음 — 가짜 WS 서버(메시지를 주입하는 async 제너레이터)와 가짜 깊이 캐시를 쓴다.

**캐시·커넥터**
- 캐시에 심볼 깊이가 있고 TTL 안이면 `Row.depth_asks`/`depth_bids` 가 그 값, `depth_at` 이 수신 시각
- TTL(10초)을 넘긴 항목 → 두 목록이 빈 채로, `depth_at` 은 null
- 캐시에 없는 심볼 → 빈 목록. `asks`/`bids` 는 REST 값 그대로 (1단계)
- 누적 1,000,000 USDT 에서 잘린다. 첫 단계가 이미 상한을 넘어도 1단계는 남는다
- 국내 커넥터의 `Row` 는 `depth_*` 가 항상 빈 목록

**샤딩·구독**
- 심볼 300개 → 3샤드에 분산되고, 같은 심볼은 항상 같은 샤드
- 심볼이 추가·삭제돼도 나머지 심볼의 샤드 배정이 바뀌지 않는다
- SUBSCRIBE 한 메시지의 스트림 수 ≤ 100
- 60초 재조정: 새 심볼 구독·사라진 심볼 해지 및 캐시 삭제

**watchdog**
- 구독 중인데 30초 무수신 → 그 사이클이 `stale_stream` 으로 실패 기록되고, 표의 바이낸스 행은 직전 스냅샷으로 유지된다
- **샤드 3개 중 1개만** 30초 무수신이어도 실패로 잡히고, message 에 그 샤드 번호가 담긴다(나머지 2샤드가 메시지를 받는 중이어도 마찬가지)
- 여러 샤드가 정체면 message 가 가장 오래 조용한 샤드를 가리킨다
- 구독이 0개인 샤드는 아무리 조용해도 판정에서 빠진다(구독 있는 샤드가 방금 받았으면 정체 아님)
- 무수신이 30초 미만이면 실패로 치지 않는다
- 메시지가 다시 오면 다음 사이클이 성공으로 기록돼 구간이 닫힌다
- 구독 대상이 0개면(기동 직후) 무수신이어도 실패가 아니다

**장애**
- 소켓 연결 실패로 기동 → 앱 뜨고 `/health` 200, `/spreads` 정상(깊이 빈 목록), 경고 로그 1줄
- 연결이 끊기면 백오프로 재시도하고, 붙으면 다음 메시지로 캐시가 복구된다
- 샤드 1개만 죽으면 나머지 2샤드의 심볼은 깊이를 유지한다
- 앱 종료 시 샤드 태스크가 취소되고 소켓이 닫힌다(종료 로그에 잔여 예외 없음)

**회귀**
- `/spreads` 응답이 이 스펙 전후로 동일하다(계약 무변경)
- 사이클당 바이낸스 REST 호출 수는 여전히 2

수동: 서버 기동 → 60초 뒤(첫 재조정, §3.3) 로그에 샤드 3개 구독 완료, 임의 심볼의 `depth_asks` 길이가 2 이상. 네트워크를 끊으면 30초 뒤 `/health/collect` 의 바이낸스가 `stale_stream` 구간을 보이고, 복구하면 닫힌다.

- 추측한 지점 (묻지 않고 정한 사소한 것) / 실행 중 함께 고친 스펙 절:
  - **캐시 키**를 바이낸스 원본 심볼 대문자로 정했다(§3.4 에 적음). 스트림 이름과 `native_symbol` 이 같은 값이라 base↔symbol 변환이 사라진다.
  - **정체 예외**는 `exchange_api_error`(`kind="stale_stream"`, `url`·`status_code` null)로 던진다. 전용 예외 클래스를 만들지 않은 이유는 011 의 경로가 `kind` 만 보기 때문이다. 이 때문에 `ExchangeError.url` 을 `str | None` 으로 넓혔다(§3.4·§3.6 에 적음).
  - **상한 자르기 위치**를 캐시 쓰기가 아니라 커넥터의 `Row` 조립으로 정했다(§3.5 에 적음). 가짜 캐시를 넣는 테스트에서도 상한이 보장된다.
  - **무수신 기준 시각**(마지막 수신, 없으면 구독 시작)과 **비-깊이 프레임은 수신으로 세지 않는다**를 정했다(§3.2·§3.6 에 적음). 구독 응답만 오고 깊이가 멈춘 소켓을 정상으로 보지 않기 위해서다.
  - **첫 구독 시점**: 소켓은 기동 즉시 붙지만 그때 LiveStore 가 비어 있어 실제 구독은 첫 재조정(최대 60초)에 일어난다. §3.3 에 적고 §4 수동 항목의 "30초 뒤" 를 "60초 뒤" 로 고쳤다.
  - **백오프 리셋 시점**을 "구독까지 성공했을 때" 로 정했다(§3.3 에 적음). 연결만 되고 바로 끊기는 소켓에서 백오프가 자란다.
  - **종료 시 소켓 close 상한 2초**를 §3.4 에 추가했다. 실서버 종료를 재보니 순차 close 로 **22초**가 걸렸다 — 배포의 `docker stop`(10초)보다 길어 SIGKILL 이 난다. 동시 close + 상한으로 3초가 됐다.
  - 재조정 대기는 별도 태스크 없이 `recv()` 에 남은 시간을 타임아웃으로 걸어 처리한다(websockets 문서가 보장하는 취소 안전성). 샤드 1개 = 태스크 1개다.
  - 안정 해시는 `zlib.crc32`. `hash()` 는 `PYTHONHASHSEED` 때문에 프로세스마다 달라져 재기동 시 전 종목이 재배정된다 — 서브프로세스 2개로 검증하는 테스트를 뒀다.
  - **여러 샤드가 동시에 정체일 때 message 가 가리킬 샤드**를 정했다: 가장 오래 조용한 샤드, 동률이면 작은 번호(§3.6 에 적음). 구간은 1건인데 message 는 하나뿐이라 고를 수밖에 없고, 가장 오래 죽어 있는 쪽이 사람이 먼저 볼 값이다.
  - **정체 여부를 읽는 방법**을 불리언에서 `StalledShard | None`(샤드 번호 + 그 샤드 구독 수)로 바꿨다. message 에 두 값을 담으라는 §3.6 요구를 커넥터가 캐시를 한 번만 읽고 만족하려면 판정 결과가 그 두 값을 들고 와야 한다 — §3.4 의 "커넥터가 캐시에서 읽는 것은 심볼 조회와 정체 여부 둘뿐"은 그대로다.
  - **구독 수가 0 으로 줄어든 샤드**는 그 시점부터 판정 대상에서 빠지고, 다시 구독이 생기면 무수신 시계를 그 순간부터 새로 센다(0 → 양수 전이에서만 시작 시각을 찍는다). 재조정으로 잠깐 빈 샤드가 곧바로 30초 정체로 잡히지 않게 하기 위해서다.
