# 009 — tick-store

상태: TODO | 의존: 001(collect — 사이클·LiveStore), 003(spreads — 김프 수식·`/spreads`), 005(history — Influx 모델·`/history/*`), 007(deploy — compose)

> 이 문서는 이 기능이 **지금 어떻게 동작해야 하는지**를 적는다. 동작이 바뀌면 이 문서를 직접 고치고, 같은 PR 에서 코드·테스트도 맞춘다(CLAUDE.md §4·§6). 사람이 끝까지 읽는 문서다 — 코드를 산문으로 옮기지 않는다.

## 1. 목적
김프 역사를 **한 초도 빠짐없이** 남긴다. 저장을 세 계층으로 나누고, 매초 만든 **틱 레코드** 하나가 그 세 계층을 순서대로 흐르게 한다.

```
매초   수집 사이클 ─→ 틱 레코드 생성
                        │
         ┌──────────────┴───────────────┐
         ▼                              ▼
   ① LiveStore (메모리)          ② Redis Stream
      최신 상태 1장                 최근 1시간 창, 전량 append
      조회가 읽는 곳                       │
                                          │ 60초마다 커서 이후 전량
                                          ▼
                                   ③ InfluxDB `premium`
                                      영구 역사, 초단위
```

각 계층의 책임은 겹치지 않는다.

- **① LiveStore** — "지금"을 답한다. 1초마다 통째 교체되는 최신 상태. `/spreads` 가 읽는 유일한 곳이고, 폴링 경로에 Redis·Influx 호출이 없다.
- **② Redis Stream** — "아직 DB 로 옮기지 못한 구간"을 들고 있는 버퍼. 매초 엔트리 1건이 쌓이고, 옮겨진 뒤에도 창(1시간) 안에서는 남아 있다.
- **③ InfluxDB** — 영구 역사. 스트림에 쌓인 구간을 **통째로** 받아 초단위 해상도로 보존한다. `/history/*` 가 읽는 곳.

②에서 ③으로 갈 때 고르거나 솎아내지 않는다. 스트림에 들어간 틱은 전부 DB 에 들어간다.

## 2. 범위
- 만드는 것: core 의 Redis 클라이언트(연결·스트림 쓰기/읽기), 수집 사이클 끝의 **틱 생성·적재**, **flusher**(스트림 구간을 Influx 로 일괄 적재, 커서 보유), **spark 캐시**(코인별 최근 30개, 재기동 복원), dev·배포 compose 의 `redis` 컨테이너, env `REDIS_URL`.
- 자리를 넘기는 것: 005 의 persist 루프가 하던 Influx 쓰기는 flusher 가 맡는다. Influx 스키마(`premium`·`dw_fail`)·수식·실패 격리 규칙은 005 그대로다.
- 값이 채워지는 것: `/spreads` 행의 `spark`, 그리고 010 이 S3 로 올리는 스냅샷 줄의 `spark`. 키·타입은 불변이라 FE 는 하위호환.
- 하지 않는 것: FE 스파크라인 렌더(후속 — FE 는 이미 `spark: number[]` 타입 보유). 초단위 조회 API(후속 — `/history/*` 는 계약 그대로). Influx 보존·롤업 정책(용량은 인프라 확장 전제로 배제한다는 사용자 방침 — 과부하 테스트 후 별도 스펙). `/spreads` 응답 계약 변경(값만 채워진다). 수집기/API 프로세스 분리(후속).

## 3. 동작

### 3.1 읽는 계약 (복사)
- 001: 수집 사이클은 1초 주기이고, 끝에 LiveStore 를 거래소 단위로 통째 교체한 뒤 수신 시각을 갱신한다. 사이클은 예외를 밖으로 던지지 않는다. collector 는 그 사이클에 입출금 조회가 실패한 거래소 목록을 들고 있고, 이 목록은 사이클마다 통째로 덮어써진다.
- 003: 김프 **원값** 수식 — `fwdRaw = premium_percent(buy_krw=fx_ask×rate_ask, sell_krw=dom_bid)`, `revRaw = premium_percent(buy_krw=dom_ask, sell_krw=fx_bid×rate_bid)`. 최우선 1단계 기준이고 체결 규모와 무관하다. 조합 자격: **국내 × 해외가 서로 다른 거래소**여야 하고, 양쪽 호가가 있어야 하고, 그 국내 거래소 자신의 USDT 시세가 있어야 하며, 여섯 값 중 ≤0 이면 건너뛴다.
  `/spreads` 응답의 `fwd`·`rev` 는 슬리피지 차감 후 순값이라 **이 스펙이 저장하는 값과 다르다** — 저장은 규모에 의존하지 않는 원값만 한다.
- 005: Influx `premium` = tag(dom·fx·base) × time(초) × field(fwd·rev). **같은 태그+시각은 덮어쓴다** — 이 스펙의 재시도 안전성이 여기 기댄다. `dw_fail` = 입출금 조회 실패가 관측된 거래소마다 1점. 쓰기 실패는 `DB 저장 실패 (연속 n회)` 로그 후 다음 회차.

### 3.2 틱 레코드
세 계층을 흐르는 단위이며, 모양은 하나다.

```
{ ts, rows, dwFailed }
```

- `ts` — 수집 시각(epoch 초). Influx 점의 `time` 이 되는 값.
- `rows` — 그 사이클에 §3.1 자격을 통과한 조합 배열 `[{dom, fx, base, fwd, rev}…]`. 현재 약 490 개.
- `dwFailed` — 그 사이클에 입출금 조회가 실패한 거래소 이름 배열. `dw_fail` 점의 원천이다.

`rows` 원소가 곧 Influx `premium` 점의 모양이라 계층을 넘을 때 변환이 없다. `dwFailed` 를 틱에 실어 두므로 flusher 는 collector 의 가변 상태를 읽지 않아도 되고, `dw_fail` 점의 시각이 그 틱의 `ts` 로 확정된다.

### 3.3 계층 ① LiveStore
- 001 이 정의한 대로 최신 호가 스냅샷과 환율을 들고, 1초마다 통째 교체된다. 이 스펙은 그 동작을 바꾸지 않는다.
- 여기에 **spark 맵**이 추가로 게시된다(§3.7). `/spreads` 는 행을 조립할 때 이 맵을 읽는다.
- 조회 경로(`/spreads`)는 LiveStore 만 읽는다. Redis·Influx 를 부르지 않는다.

### 3.4 계층 ② Redis Stream
- 컨테이너 `redis`(7-alpine), compose 내부 전용(호스트 비노출), `appendonly yes`, named volume — 재기동해도 창이 보존된다.
- env `REDIS_URL`(기본 `redis://localhost:6379/0`). compose 는 007 의 `INFLUX_URL` 패턴대로 `redis://redis:6379/0` 을 `environment` 로 오버라이드한다. `server/.env.example` 에 키 추가.
- 키는 하나: **`hist:ticks` Stream**. 사이클당 1엔트리.
  ```
  XADD hist:ticks MAXLEN ~ 3600 * ts <ts> data <gzip JSON>
  ```
- `data` 는 §3.2 틱 레코드를 gzip 한 JSON. 조합 490개면 원본 ~30KB, 압축 후 ~3KB — 창 전체가 약 10MB 다.
- **창 3600 = 1시간**은 flusher 주기(60초)의 60배다. Influx 가 한 시간 넘게 막히지 않는 한 유실이 없다는 여유분이고, 이 값을 줄이면 그만큼 장애 내성이 줄어든다. `~` 는 근사 트리밍(Redis 가 노드 경계에서만 자른다). 창 길이는 코드 상수.

### 3.5 틱 생성·적재 (수집 사이클 끝, 매 1초)
- 메모리 교체가 끝난 뒤, §3.1 의 수식·자격으로 전 조합의 fwd/rev 를 계산하고 collector 의 입출금 실패 목록을 함께 담아 §3.2 의 틱 레코드를 만든다.
- 만든 틱을 스트림에 XADD 한다.
- `rows` 와 `dwFailed` 가 **둘 다 비면** 적재하지 않는다 — 실을 값이 없고, 빈 엔트리는 창만 차지한다. (`rows` 가 비는 대표적 경우: 어느 국내 거래소에서도 USDT 시세를 받지 못해 모든 조합이 자격 미달.)
- 적재는 사이클의 마지막 단계이고, 실패해도 사이클은 성공으로 끝난다.

### 3.6 계층 ③ Influx — flusher (60초)
주기 60초는 코드 상수다. 기동 후 먼저 60초 잔 뒤 첫 회차. 회차마다:

1. **커서 이후의 엔트리를 전부** 읽는다 — `XRANGE hist:ticks (<커서> +`. 커서가 없으면 창의 처음부터. 비면 이번 회차 생략.
2. 읽은 **모든 틱의 모든 조합**을 `premium` 점으로, `dwFailed` 를 `dw_fail` 점으로 변환해 보낸다. 각 점의 `time` 은 그 틱의 `ts` 다. 한 회차는 약 60틱 × 490조합 ≈ 2.9만 점이라 배치 크기(코드 상수, 기본 5,000점)로 나눠 보내고, **모든 배치가 성공해야 회차 성공**이다.
3. 회차가 성공하면 커서를 마지막으로 적재한 엔트리 ID 로 옮긴다. 실패하면 커서를 두고 다음 회차가 같은 구간부터 다시 보낸다.

- **무유실의 근거**: 같은 (태그, 시각) 점을 Influx 가 덮어쓰므로 중복 적재는 무해하고, 커서가 성공할 때만 전진하므로 유실이 없다. 실패는 구멍이 아니라 지연이며, 창(1시간)을 넘겨 밀렸을 때 비로소 유실이 된다.
- 커서는 메모리에 둔다. 재기동하면 창의 처음부터 다시 적재되고 기존 점을 덮어쓴다 — 결과는 같고, 그 첫 회차만 최대 3600 엔트리(약 180만 점)로 무겁다. 배치 분할이 이를 감당한다.
- flusher 는 LiveStore 도 collector 상태도 읽지 않는다. 원천이 스트림뿐이라 **수집 락을 잡지 않는다.**
- 실패 처리는 005 그대로: `DB 저장 실패 (연속 n회)` 로그, 다음 회차 재시도, 회차 안 예외는 밖으로 던지지 않는다.
- **적재량**: 490조합 × 86,400초 ≈ 하루 **4,200만 점**. 전 구간 streaks 쿼리가 Influx 를 재시작시킨 실측(status.md 알려진 빚)이 있으므로 이력 조회는 범위를 좁혀 쓰고, 보존·롤업은 과부하 테스트 후 별도 스펙으로 정한다.

### 3.7 spark — `/spreads` 행의 김프 추이
- 정의: 행(dom, fx, base)마다 **fwd 의 최근 30개, 벽시계 1분 간격, 오래된 → 최신**. 30개 미만이면 있는 만큼. 30분 추이를 작은 그래프로 보여주는 값이다.
- 간격은 **벽시계 분 경계**로 정한다 — 틱의 `ts` 를 60 으로 나눈 분 버킷마다 그 버킷의 마지막 틱 fwd 하나를 취한다. flusher 주기를 바꿔도 spark 간격은 변하지 않는다.
- flusher 회차마다 그 회차가 읽은 틱들에서 위 규칙으로 값을 뽑아 코인별 링버퍼(최대 30)에 밀어 넣고, 완성된 맵을 LiveStore 에 게시한다.
- **재기동 복원**: 기동 시 스트림에서 최근 30분을 같은 분 버킷 규칙으로 훑어 링버퍼를 채운다. 스트림이 비면 빈 채로 시작해 회차마다 찬다.
- `status` 가 `fail` 인 행도 spark 는 그대로 싣는다 — 추이는 추이다.

### 3.8 장애 격리
- **Redis 불달**: 기동 시 연결 실패는 경고 로그 1줄이고 앱은 뜬다. 수집·`/spreads` 는 정상이고 `spark` 는 빈 배열이다. 틱 적재는 사이클마다, flusher 는 회차마다 다시 시도한다.
- **Influx 불달**: 005 규칙 그대로. 스트림은 계속 쌓이고 커서가 멈춰 있다가, 복구되면 밀린 구간이 한 번에 들어간다.
- 어느 쪽 장애도 수집 사이클과 조회 경로를 세우지 않는다.

### 3.9 compose
- dev(`docker-compose.dev.yml`)와 배포(`docker-compose.yml`) 둘 다에 `redis` 서비스 — 이미지 `redis:7-alpine`, `--appendonly yes`, named volume, 호스트 비노출, server 의 `REDIS_URL` 오버라이드. 배포 가드·기존 컨테이너 무접촉 규칙(007)은 그대로.

## 4. 검증
네트워크 없음(fakeredis 로 Redis 를 흉내낸다 — dev 의존성 추가 허용).

**틱 적재**
- 사이클 1회 → 엔트리 1건. 압축을 풀면 조합 수·fwd/rev 가 같은 시드의 `/spreads` 계산과 일치하고, `ts` 가 수신 시각과 같다
- 사이클 3회 → 엔트리 3건, `ts` 가 증가한다
- 입출금 조회 실패가 관측된 사이클 → 그 틱의 `dwFailed` 에 거래소 이름이 담긴다
- `rows`·`dwFailed` 가 둘 다 빈 사이클 → 엔트리 없음
- Redis 불달로 기동 → 앱 기동·수집·`/spreads` 정상(`spark` 빈 배열), 경고 로그 1줄, 사이클 계속

**flusher**
- 스트림이 비면 회차 생략(Influx 쓰기 0회)
- 틱 N건이 쌓인 뒤 회차 → `premium` 점 수 = N건의 조합 수 합계, 각 점의 `time` 이 해당 틱의 `ts` 와 일치
- `dwFailed` 가 있는 틱 → 그 거래소·그 `ts` 로 `dw_fail` 점이 생긴다
- 커서: 회차 후 틱을 더 쌓고 다음 회차 → 새로 쌓인 구간만 적재된다
- 실패 재시도: 회차가 실패하면 커서가 그대로이고, 다음 회차가 같은 구간을 다시 보내 유실이 없다
- 멱등: 같은 구간을 두 번 적재해도 점 수·값이 변하지 않는다
- 배치 분할: 배치 상수보다 큰 구간도 전부 적재되고, 한 배치가 실패하면 회차 실패로 커서가 멈춘다
- flusher 회차 중 수집 사이클이 지연되지 않는다(락 미획득)

**spark**
- 서로 다른 분 버킷의 틱 2건 → spark 길이 2, 오래된 → 최신
- 같은 분 버킷의 틱 여러 건 → 그 버킷의 마지막 값 1개만 들어간다
- 31개 버킷이 지나도 길이 30 유지
- 스트림을 30분치로 시드하고 기동 → spark 가 복원된다
- Redis 없으면 빈 배열
- `fail` 행도 spark 가 유지된다

**응답**
- `/spreads` 행 17키·최상위 키 불변(`spark` 만 값이 찬다), 기존 테스트 전부 통과
- 010 스냅샷 줄 21키 불변, `spark` 에 실값이 실린다
- 적재된 `premium` 점의 fwd 가 같은 시각 `/spreads` 응답의 `fwd + slipFwd` 와 같다(원값 저장 고정)

**수동**: dev compose(redis+influx) 기동 → 2~3분 뒤 `/spreads` 행에 spark 1~3개. `docker compose exec redis redis-cli XLEN hist:ticks` 가 초당 1씩 증가하고 3600 부근에서 멈춘다. `/history/premium?base=BTC` 의 count 가 회차마다 약 60씩 증가한다. Redis 컨테이너를 내려도 `/spreads` 는 계속 갱신되고, 다시 올리면 적재가 재개된다. Influx 컨테이너를 1분 내렸다 올리면 밀린 구간이 한 번에 들어가 count 에 구멍이 없다.
