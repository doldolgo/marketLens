## 1. 목적
해외 perp 거래소 두 곳 사이의 **선선갭** — 같은 코인의 가격 차이와 **시간당으로 정규화한 펀딩 차이** — 를 실데이터로 본다. 끝나면 선선갭 탭이 mock 대신 매초 오는 표로 돌고, 트레이더가 "어느 코인을 어디서 롱하고 어디서 숏하면 가격이 몇 % 벌어져 있고 시간당 펀딩을 얼마나 받는가"를 본다. 거래소마다 펀딩 주기(1·4·8시간)가 달라 **시간당**으로 맞춰야 비교가 된다.
가격갭도 048 과 같이 **체결 가능한 최우선 호가**(싼 쪽 ask 에 롱, 비싼 쪽 bid 에 숏)로 계산한다(2026-10-08 사람 결정).

## 2. 범위
- 만드는 것: server — 틱마다 선선갭 표 1장(접속자와 무관하게 매초), Redis 게시(채널 `pp`·키 `pp:latest`), 048 이 일반화한 허브의 세 번째 인스턴스 `GET /ws/pp`. web — `features/pp` 의 mock 피드를 `/ws/pp` 구독으로 교체(화면·조작은 002 §3.8 그대로). nginx 공개 허용 목록에 `/api/ws/pp`. mock 공통(002 §3.6)의 선물 항목 규칙은 pp 가 마지막 사용자라 함께 지운다.
- 하지 않는 것: 이력 저장·사건·봉, 슬리피지 차감, HTTP 조회 `GET /pp`, 현물이 낀 조합(048), 입출금, 세 곳 이상을 묶는 조합, 펀딩 예측값(다음 주기 추정 — 거래소가 주는 현재 값만), 관리자 화면의 pp 접속 수.
- 바꾸는 기존 것: 028 허용 목록 +1(§3.4), 002 §3.6·§3.8 의 mock 규칙 삭제(§6). 048 의 허브·게시기 코드는 **고치지 않고** 표 id 만 하나 더 꽂는다 — 고쳐야 한다면 048 스펙의 결함이므로 멈추고 048 을 먼저 고친다.

## 3. 동작

### 3.1 읽는 계약 (복사)
- 046 §3.1 perp 행 = `(source, base)` 당 `bid`·`ask`·`bid_size`·`ask_size`(1코인 단위 — 배수 심볼은 046 이 나눠 둔 값)·`funding_rate`(한 주기의 비율, null 가능)·`next_funding_ms`(null 가능)·`funding_interval_h`(정수 시간, null 가능)·`updated_at`. 원천 고정 순서 `binance_perp`·`bybit_perp`·`bitget_perp`·`hyperliquid_perp`, 표시명 `Binance`·`Bybit`·`Bitget`·`Hyperliquid`. 원천별 스트림 상태 `last_message_at`.
- 003 §3.2 `age`·`status`: `age` = 양쪽 스트림 `last_message_at` 중 오래된 쪽의 경과 초(0 미만이면 0), 두 행 중 어느 쪽이든 `updated_at` 이 300초 이상 오래됐으면 그 행의 실제 경과 초(둘 중 오래된 쪽). `status` = 최우선 호가 4개 중 하나라도 없거나 가격·잔량이 0 이하면 `fail`(숫자 필드 0), `age ≥ 5.0` 이면 `stale`, 아니면 `ok`. `premium_percent(buy, sell) = (sell / buy − 1) × 100`(`core/premium.py`).
- 048 §3.3~3.4: 게시 = 틱 루프 안에서 표를 만들어 큐 → 별도 태스크가 `PUBLISH <id> <JSON>` + `SET <id>:latest <JSON> EX 10`(큐 2장, Redis 불달 60초 1줄, 300ms 경고). 허브 = 표 id 하나로 매개변수화(채널·시작 키·경로 `/ws/<id>`·행 키 함수), 프레임 `snapshot`·`delta`(`rows` + `removed`)·`heartbeat`·`waiting`, 바이너리 gzip JSON, 바뀜 = `age` 뺀 어느 필드. web 구독 = 탭이 보이는 동안만 연결, 숨으면 닫고 `age` 만 키움, 다시 보이면 snapshot 교체, 017 §3.4 의 연결·재연결 규칙.

### 3.2 표 계산 (틱 루프 안, 동기)
- 조합 = (perp 원천 `a`, perp 원천 `b`, **양쪽에 행이 있는** base), `a` 가 `b` 보다 원천 순서에서 앞 — 순서 없는 쌍 하나가 행 하나다(코인당 최대 6행). 코인 범위 = perp 우주 전체(046 — 국내 상장과 무관).
- 행 값(반올림하지 않는다):
  ```
  longA = premium_percent(buy=a_ask, sell=b_bid)   # a 에서 ask 에 롱, b 에서 bid 에 숏 — 양수면 b 가 비싸다
  longB = premium_percent(buy=b_ask, sell=a_bid)   # b 에서 롱, a 에서 숏
  ```
  두 값은 보통 둘 다 음수(스프레드)거나 한쪽만 양수다 — 한 행에 둘을 다 싣고 방향 선택은 화면이 한다. 펀딩은 양쪽을 그대로 싣는다: `fundA`·`fundB` = `funding_rate × 100`(한 주기 퍼센트, null 가능), `intA`·`intB` = `funding_interval_h`(null 가능), `nextA`·`nextB` = `next_funding_ms // 1000`(epoch 초, null 가능). **시간당 펀딩과 펀딩갭은 서버가 계산하지 않는다** — 화면이 `fund / int` 로 만든다(§3.5). 이유: 행에 파생값을 더하면 키가 늘고, 방향(누가 롱인가)에 따라 부호가 바뀌어 서버가 정할 수 없다.
- `status`·`age` 는 003 §3.2 그대로(호가 4개 = a·b 의 bid/ask 가격·잔량). `fail` 이면 `longA`·`longB` 는 0, 펀딩 여섯 값은 그대로.
- 행 정렬 `(sym, a, b)` 오름차순 — `a`·`b` 는 원천 순서.
- 표 JSON: `{"rows":[…], "warnings":[], "dataReceivedAt":<틱 ts, 초>, "fetchedAt":<ms>}`. 행 키 **13개** 고정: `sym a b longA longB fundA intA nextA fundB intB nextB status age`. 예:
  ```json
  {"sym":"BTC","a":"binance_perp","b":"hyperliquid_perp","longA":-0.0021,"longB":0.0009,
   "fundA":0.0011,"intA":8,"nextA":1791475200,"fundB":0.00125,"intB":1,"nextB":1791464400,"status":"ok","age":0.4}
  ```
- 규모: perp 우주 약 450코인 × 최대 6쌍 = **최대 약 2,700행**(코인마다 원천 2~4곳이라 실제는 1,500행 안팎). 조합을 한 번 훑고 불변 튜플형 레코드로 만든다. 단계별 소요 로그에 `선선표` 단계.

### 3.5 web — 선선갭 탭
- 화면·조작·정렬·강조·빈 상태는 002 §3.8 그대로. 바뀌는 것은 데이터 원천과 코인별 집계·펀딩 계산이다.
- 구독·표시명·키 규칙은 048 §3.6 과 같다(`/ws/pp`, 탭이 보일 때만, 표시명 `binance_perp→Binance` …, 행 키 `sym|a|b`, 안 실린 행의 `age` 되돌리기).
- 시간당 펀딩 `fundH = fund / int`(퍼센트/시간, `fund` 또는 `int` 가 null·0 이면 null). 거래소별 주기 상수표(Hyperliquid 1·Bitget 4·그 외 8)는 **없앤다** — 행의 `intA`·`intB` 가 심볼마다 말한다.
- 집계(렌더마다 행을 한 번 훑어 코인별 누산): `fail` 아닌 행마다 두 방향을 본다 — 방향 = (롱 원천, 숏 원천, 가격갭, 펀딩갭). `longA` 방향은 (a, b, `longA`, `fundH_B − fundH_A`), `longB` 방향은 (b, a, `longB`, `fundH_A − fundH_B`). **펀딩갭 = 숏 쪽 시간당 펀딩 − 롱 쪽 시간당 펀딩** — 양수면 그 포지션이 시간당 받는 퍼센트(숏은 펀딩을 받고 롱은 낸다 — 펀딩이 양수일 때). 어느 한쪽 `fundH` 가 null 이면 그 방향의 펀딩갭은 null.
  - **채택 가격갭 방향** = 가격갭 최대인 방향(동률이면 원천 순서가 앞선 롱 쪽). 가격갭 열·롱/숏 칩·`age`·펀딩갭 열은 전부 이 방향에서 온다(002 §3.8 "펀딩갭 열은 채택 가격갭 쌍의 펀딩 차").
  - **채택 펀딩갭 방향** = 펀딩갭(null 제외) 최대인 방향 — `임계 초과만` 토글의 연환산 비교(`펀딩갭 × 24 × 365 ≥ 펀딩갭 임계값 · 연`)에만 쓴다(002 §3.8 그대로).
  - `fail` 행뿐인 코인은 fail 행(값 `–`, 항상 뒤). stale = 채택 방향 행 `age ≥ 5`. hot = 가격갭 ≥ 임계.
- 가격갭 셀 2줄 = `{롱 표시명}` 칩 `↔` `{숏 표시명}` 칩 + 가격갭(굵게, 퍼센트 색 — 음수면 파랑으로 보이는 것이 맞다: 최우선 호가로는 벌어진 게 없다는 뜻) / `{롱} 롱 / {숏} 숏`. 펀딩갭 셀 2줄 = 채택 방향 펀딩갭을 소수 4자리 `%/h`(null 은 `–`) / `해당 조합 펀딩갭`.
- 빈 상태: 행 0 개(`waiting` 포함) → `백엔드에서 선선갭 표를 받는 중입니다…`. URL 키 `p.*` 그대로(검색어 제외).

### 3.6 엣지
- 원천 하나가 끊기면 그 원천이 낀 행들이 `age` 로 stale. 코인에 남은 원천이 하나뿐이면 행이 없다(쌍이 안 된다) — 다음 delta 의 `removed`.
- Hyperliquid 펀딩은 매시간이라 `intB = 1`, `nextB` 는 다음 정시 — 시간당 정규화에서 그대로 1 로 나뉜다. 바이낸스는 심볼마다 4·8 시간이 섞여 있다(046) — 같은 거래소 안에서도 `int` 가 다를 수 있으므로 행마다 값을 쓴다.
- 배수 심볼(`1000PEPE`·`kPEPE`)은 1코인 단위로 나눠져 와서 `PEPE` 한 행으로 비교된다(046).

## 4. 검증
네트워크 없음 — 가짜 저장소·가짜 Redis(017·048 의 fakes 재사용).
- `longA`·`longB` 식: a ask 100·bid 99.9, b ask 100.3·bid 100.2 → `longA = 0.2`, `longB = (99.9/100.3 − 1)×100`. 같은 쌍은 (a, b) 한 행이고 (b, a) 행은 없다. 정렬 `(sym, a, b)` 원천 순서.
- 코인 범위가 perp 우주 전체 — 국내 상장이 없는 코인도 행이 있다. 원천이 하나뿐인 코인은 행 없음. 세 곳이면 3행, 네 곳이면 6행.
- `status`: 호가 4개 중 하나라도 없거나 0 → `fail`(`longA`·`longB` 0, 펀딩 실림). `age ≥ 5` → `stale`. 300초 예외.
- 표 JSON: 행 키 정확히 13개, `warnings` 빈 목록, NaN 거부. 2,700행 표 생성 시간 측정(§5).
- 게시·허브: 채널 `pp`·키 `pp:latest`·`/ws/pp`, 행 키 `sym|a|b`, `removed` 형식, snapshot·waiting·heartbeat·1008, 세 허브(spreads·gap·pp)가 서로의 채널을 받지 않고 spreads 바이트는 그대로. 048 의 허브 코드 diff 가 0 이다(표 id 등록만).
- nginx 계약 테스트: `/api/ws/pp` 정확 일치·업그레이드 헤더, `/api/ws/pp/` 404, 웹 호출 경로 대조 통과.
- web: `npm run lint && npm run build`. 집계 — 두 방향 중 가격갭 최대 방향 채택·동률이면 원천 순서 앞선 롱, 펀딩갭 부호(숏 − 롱), `fundH` null 전파, 연환산 비교는 펀딩갭 최대 방향, 음수 가격갭 파랑, 거래소별 주기 상수가 코드에서 사라짐, 탭 숨김·복귀 시 연결 닫힘·snapshot 교체, `임계 초과만` 토글이 002 §4-7 과 같이 동작.
- 수동(실서버): `redis-cli GET pp:latest | head -c 400` 에 13키 행, `/api/ws/pp` snapshot → delta, 선선갭 탭에서 BTC 의 Binance↔Bybit 가격갭이 두 거래소 화면의 호가와 맞고 Hyperliquid 행의 펀딩이 `%/h` 로 시간당 값이다. 실측해 §5 에: 행 수, 표 생성 ms(`선선표`), snapshot·delta 바이트, collect 박스 CPU 증가분(046·048 뒤 누적).
