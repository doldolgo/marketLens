# 스프레드 웹소켓 부하 측정 (사람용 절차 + 2026-09-26 기록)

`/api/ws/spreads` 에 가짜 접속자를 계단식으로 붙여 "동시 접속자 몇 명까지 매초 표가 제때 오는가" 를 재는 절차와,
처음 잰 날의 결과·그 결과로 내린 결정을 시간순으로 남긴다. 나중에 다시 잴 때 같은 방법으로 재야 숫자를 비교할 수 있다.

## 1. 왜 이 방식인가

- **도구는 Python `websockets` 클라이언트**(`server/tools/ws_loadtest.py`)다. k6 를 쓰지 않은 이유 — k6 의 웹소켓 모듈은
  permessage-deflate 를 협상하지 않아서 서버가 압축 없이 보내 버린다. 개선 전 서버는 접속마다 압축을 했으므로, 압축을 협상하지
  않는 도구로는 그 비용이 측정에서 빠진다. `websockets` 는 브라우저처럼 기본으로 협상한다. 스크립트는 첫 접속의
  `Sec-WebSocket-Extensions` 응답 헤더를 마지막 줄에 찍으므로 어느 조건으로 쟀는지 결과에 남는다.
- **부하 생성기는 서버와 같은 리전의 EC2** 다. 접속자 1명이 매초 250~350KB(압축 해제 기준)를 받으므로 200명이면 초당 수십 MB 가
  내려온다. 집 회선에서 쏘면 서버보다 생성기 쪽 회선이 먼저 막혀 결과가 왜곡된다.
- **실서버에 직접 쏜다**(2026-09-26 결정, 이용자가 거의 없을 때). 로컬 M4 는 t4g.micro 와 성능이 달라 절대값이 안 나오고,
  serve 구성을 복제한 박스를 따로 띄우는 것은 비용 대비 이득이 없었다. 테스트 중 실제 이용자는 끊길 수 있다.
- **가짜 접속자는 브라우저와 같은 재접속 동작**을 한다 — 끊기면 1초 뒤 다시 붙는다. 과부하에서 재접속 폭풍이 생기는지까지 보기 위해서다.
- 단계마다 접속을 초당 20개씩 늘리고(접속 폭주가 아니라 유지 부하를 재는 것), 늘리는 구간의 숫자는 버리고 유지 구간 30초만 집계한다.

## 2. 절차

1. 부하 생성기: 서울 리전 `c7g.medium`(ARM, Ubuntu 24.04), serve 와 같은 서브넷·보안그룹·키페어. 2026-09-26 에 만든
   `marketlens-loadgen`(`i-0f67a2b7fef4ae3b1`)이 **정지 상태로 보관**돼 있다 — 시작하면 퍼블릭 IP 가 바뀌므로 `~/.ssh/config` 의
   `Host loadgen` 을 고친다. 홈에 `v/`(venv, websockets 설치됨)와 스크립트가 있다. 새로 만들면:
   ```bash
   sudo apt-get install -y python3.12-venv && python3 -m venv v && v/bin/pip install websockets
   scp server/tools/ws_loadtest.py loadgen:~/
   ```
2. 서버 쪽 관찰을 먼저 켠다(다른 터미널):
   ```bash
   ssh serve 'for i in $(seq 1 50); do echo "$(date +%T) $(docker stats --no-stream --format "{{.Name}} {{.CPUPerc}} {{.MemUsage}}" | grep api)"; sleep 4; done'
   ```
3. 부하:
   ```bash
   ssh loadgen 'ulimit -n 4096 && v/bin/python ws_loadtest.py wss://kimptrack.com/api/ws/spreads --stages 10,50,100,200,400 --hold 30'
   ```
   단계마다 한 줄이 나온다 — 살아있는 접속 수, 접속자당 초당 메시지 수(1.0 근처가 정상), 메시지 간격 p95(1초 넘게 커지면 서버가
   밀리는 것), 스냅샷 도착 시간, 끊김 코드별 수, 접속 실패(`TimeoutError` = 핸드셰이크 10초 초과).
4. 끝나면 인스턴스를 정지한다. 실서버 api CPU 가 평소(10% 안팎)로 돌아왔는지 본다.

**한계**: c7g.medium 은 vCPU 1개라 접속자 400명(압축 해제 초당 약 120MB)에서 생성기 자체가 CPU 100% 에 닿는다. 그 위를 재려면
더 큰 인스턴스와 프로세스를 나눈 스크립트가 필요하다. 2026-09-26 의 800명 시도는 이 한계로 결과가 나오지 않았다.

## 3. 2026-09-26 기록

### 3.1 개선 전 (uvicorn permessage-deflate, 접속마다 압축)

| 목표 접속자 | 살아있음 | 메시지/초/접속자 | 간격 p95 | 스냅샷 도착 p50 | api CPU |
|---|---|---|---|---|---|
| 10 | 10 | 1.21 | 1.05s | 0.15s | 16% |
| 50 | 50 | 1.08 | 1.31s | 1.5s | 57~100% |
| 100 | 100 | 0.99 | 1.74s | 4.0s (최대 8.9s) | 100% |
| 200 | 118 | 0.53 | 1.98s | 7.0s (최대 10.4s) | 100% |
| 400 | 118 | 0.29 | 1.80s | 측정 불가 | 100% |

- 50명부터 api 프로세스(uvicorn 워커 1개 = 이벤트루프 1개)가 1코어를 다 썼다. 100명에서 첫 화면까지 4~9초.
- **약 118명이 상한** — 그 위로는 핸드셰이크가 10초 안에 안 끝나 새 접속이 실패했다(200명 단계 207건, 400명 단계 743건).
- 대기열 초과로 서버가 끊는 1008 은 0건. 느린 접속자를 끊기 전에 이벤트루프 자체가 포화돼 새 접속을 못 받는 쪽으로 무너졌다.
- 메모리는 문제 없었다(api 100→134MB, caddy 22→85MB).
- 부하를 끊은 뒤에도 api CPU 가 약 70초 동안 100% 에 머물다 회복했다. 끊긴 접속의 대기열에 남은 프레임을 계속 압축·전송하다
  정리되는 것으로 보인다(개선 후에는 부하 종료 즉시 10% 이하로 떨어져 이 꼬리가 사라졌다).

### 3.2 무엇을 바꿨나 (PR #63)

원인은 uvicorn 의 permessage-deflate 가 **연결마다** 압축 상태를 따로 갖고 같은 문자열을 접속자 수만큼 압축하는 구조였다.
그래서 압축을 웹소켓 계층에서 빼서 허브로 올렸다.

- 허브가 snapshot·delta 를 만든 직후 gzip(레벨 6)으로 **표 1장당 1회** 압축하고, 접속자 전원에게 같은 바이트를 바이너리 프레임으로
  보낸다. heartbeat·waiting 도 미리 압축해 둔 같은 형식이라 브라우저가 프레임 종류를 분기하지 않는다.
- api 컨테이너의 uvicorn 을 `--ws-per-message-deflate false` 로 띄운다. 안 끄면 이미 압축한 바이트를 접속마다 또 압축한다.
- 브라우저는 소켓을 arraybuffer 로 열고 내장 `DecompressionStream("gzip")` 으로 푼다. 해제가 비동기라 도착 순서대로 직렬
  처리한다 — delta 순서가 바뀌면 병합·삭제가 틀어진다.
- gzip 레벨 6 을 고른 이유: 표 1장당 1회라 CPU 보다 크기를 택했다. 레벨 9 는 시간이 2배인데 크기 차이가 거의 없고, 레벨 1 은
  빠르지만 크기가 조금 크다. 실서버 실측 — 스냅샷 728KB → 157KB, delta 246KB → 58KB.
- 트레이드오프: (1) 배포 순간 열려 있던 탭은 옛 JS 가 바이너리를 무시하고 10초 무응답 재연결만 반복한다 — 새로고침하면 정상.
  (2) `DecompressionStream` 미지원 브라우저(Chrome 80·Firefox 113·Safari 16.4 미만)는 표가 뜨지 않는다. 폴백은 두지 않았다.
  (3) 접속자당 남는 비용이 소켓 쓰기뿐이라 다음 병목은 CPU 가 아니라 아래 3.4 의 둘이다.
- 검토했다가 버린 대안: 압축을 아예 끄기(대역폭 5~10배, t4g.micro 에서 무리), 워커 2개(vCPU 2개라 이론상 2배지만 워커마다 Redis
  구독·diff 를 중복해 이득이 반감).

### 3.3 개선 후 (같은 스크립트·같은 단계, 배포 직후)

| 목표 접속자 | 살아있음 | 메시지/초/접속자 | 간격 p95 | 스냅샷 도착 p50 | api CPU(유지 구간) |
|---|---|---|---|---|---|
| 10 | 10 | 1.45 | 1.04s | 0.36s | 7~9% |
| 50 | 50 | 1.46 | 1.07s | 0.97s | 8~10% |
| 100 | 100 | 1.40 | 1.09s | 1.1s | 9~11% |
| 200 | 200 | 1.32 | 1.05s | 2.1s | 10~12% |
| 400 | 400 | 1.25 | 1.18s | 3.9s | 13~20% |

- 400명까지 전원 연결 유지, 접속 실패 0건, 1008 0건, 매초 메시지가 제때 왔다(간격 p95 1.2초 이내).
- 400명 유지 구간 api CPU 는 13~20%. 개선 전 100명에서 100% 였던 것과 비교하면 접속자당 비용이 수십 분의 1 로 줄었다.
- 상한은 못 찾았다 — 부하 생성기(vCPU 1개)가 400명에서 먼저 포화했다(2 절 한계).

### 3.4 남은 것 (다음 병목, 순서대로)

1. **접속 폭주 시 스냅샷 압축이 접속마다** — 새 접속자에게 주는 snapshot 은 지금도 접속할 때마다 `pack(make_snapshot(...))` 을
   따로 한다(728KB gzip ≈ Graviton 에서 40~50ms). 초당 20접속으로 늘리는 구간마다 api CPU 가 95~100% 로 튀었다(유지 구간은
   10~20%). 배포 직후 전원이 동시에 재접속하는 순간이 바로 이 상황이다. 표 1장당 압축한 스냅샷을 캐시해 두면 없어진다.
2. **송신 네트워크** — 접속자 400명이면 압축 후에도 초당 약 24MB(약 190Mbps)가 나간다. t4g.micro 의 네트워크는 버스트형이라
   기준 대역폭이 낮다(AWS 문서 기준 수십 Mbps 수준, 이번 30초 측정에서는 안 드러남 — **미실측**). 수 시간 지속되는 부하에서는
   CPU 보다 이것이 먼저 한계일 수 있다.
3. 상한 자체를 알고 싶으면 부하 생성기를 c7g.xlarge 이상으로 바꾸고 스크립트를 프로세스 여러 개로 나눠야 한다.
