지적하신 것상태한 일 · 계획
수집 태스크와 조회 API가 같은 루프에서 경합한다. 수집 인스턴스를 따로 빼야 한다.1단계 완료스펙 016으로 서버를 ROLE=collector / ROLE=api 두 컨테이너로 나눴습니다. InfluxDB 조회와 스프레드 응답은 전부 api 컨테이너가 맡고, 수집기에는 헬스·분석 몇 개만 남았습니다. 아직 같은 EC2 안이라 CPU는 공유합니다. EC2 자체를 나누는 것이 5장의 계획입니다.
스프레드 API가 1초마다 56KB. 사용자 100명이면 시간당 3GB 트래픽 비용.완료스펙 017로 1초 폴링을 WebSocket 푸시로 바꿨습니다. 수집기가 표를 Redis 채널에 올리면 api가 구독해서 바뀐 행만 접속자 전원에게 같은 바이트로 보냅니다. 접속자당 244KB/s가 54~131KB/s(압축 전)로 줄었고, 접속자 수에 따라 늘던 CPU가 상수가 됐습니다. 표는 스프레드 탭을 누군가 보고 있을 때만 만듭니다. 다른 탭에서는 폴링이 없습니다.
누가 CPU를 먹는지 알아야 기능을 나눌 수 있다.완료py-spy로 수집기를 프로파일했습니다. 비트겟 전체 호가 재정렬이 47%, 바이빗 델타 처리가 22%, 표 생성의 pydantic 변환이 틱당 비용의 절반이었습니다. 각각 PR #43·#44·#45로 고쳤습니다. 자세한 수치는 3장에 있습니다.
T계열은 버스터블이라 상시 고CPU에 안 맞는다. M계열이 낫다.실험 후 보류t4g.small과 c7g.medium으로 실측했습니다. t4g.small은 크레딧이 바닥나 steal 43~53%로 수집이 무너졌고, c7g.medium은 2GB 메모리에 컨테이너 5개를 다 올려 12분 만에 죽었습니다. 지금은 t4g.medium을 유지하고, 3대로 나눌 때 수집기만 c7g.medium으로 옮깁니다. 컨테이너를 나누면 메모리가 남습니다(수집기 단독 0.35GB).
DB가 서버 안에 있으면 안 된다. RDS든 별도 서비스든 밖으로 빼야 한다.이번 주스펙 021로 Redis·InfluxDB를 별도 EC2(data 박스)로 뺍니다. 관리형(Timestream for InfluxDB)은 서울 리전 가능 여부와 가격을 아직 못 봤습니다. 7장 질문입니다.
수평 확장이 안 되는 구조다. 앞단에 로드밸런서가 있어야 한다.이번 주 1단계조회 API를 serve 박스로 떼어내는 것이 첫걸음입니다. 그 뒤 ALB + api 여러 대 구조는 infra-ha 제안서(6장)에 초안이 있습니다. 수집기는 거래소 수에만 비례하므로 로드밸런서 대신 핫 스탠바이(리더 락)로 갑니다.
로그 때문에 디스크가 터진다. 로테이트를 반드시 걸어라.컨테이너만9월 12일 디스크 풀 장애 뒤 컨테이너 로그를 json-file 50MB × 3개로 제한했습니다. 호스트 쪽 로그 보관 기간 정책(1주·1달)은 아직 없습니다.
디스크 용량은 AWS가 대신 봐주지 않는다.미착수지금 알람이 하나도 없습니다. CloudWatch 디스크·CPU 알람과 SNS 알림을 021 다음으로 잡았습니다.
nginx 액세스 로그가 없다.설명nginx는 있습니다. web 컨테이너 안에서 :80을 받아 /api/*를 프록시합니다. 호스트에 /var/log/nginx가 없는 이유는 컨테이너 안에 있기 때문입니다. 로그는 docker logs marketlens-web-1로 꺼냅니다.
없는 경로에 200을 주지 말고 404. 초당 N회 넘으면 차단.미착수SPA fallback이 모든 경로에 index.html을 돌려주고 있습니다. nginx에서 확장자 있는 경로·.env류는 404, rate limit은 limit_req로 걸 예정입니다. 토요일에 ACL 설명 듣고 진행하겠습니다.
APM 무료 플랜 세팅, 메뉴별 API 호출 시나리오.미착수부하 테스트 시나리오와 함께 토요일 이후로 잡았습니다.
451KB JS 번들 정체 확인.확인 중번들 분석 결과를 토요일에 가져가겠습니다.
S3로 옮기는 작업 공유.완료스펙 010. 거래소 원문(WebSocket 프레임·REST 응답)을 거래소별·분당 객체 1개로 raw/에 씁니다. IAM 역할로 접근하고 키는 없습니다. 하루 0.3~0.5GB로 추정했고 lifecycle은 아직 안 걸었습니다.

배포·로그·비용

  • CI: GitHub Actions. PR마다 server(ruff·pytest 542개)와 web(lint·build)을 경로 필터 없이 다 돌립니다. 문서만 바뀐 PR도 통과해야 머지됩니다.
  • 배포: main에 푸시되면 SSH로 들어가 git reset --hard 뒤 compose up -d --build. 배포 후 URL 확인과 자동 롤백은 없습니다.
  • 로그: 컨테이너마다 json-file 50MB × 3. 알람·모니터링은 없습니다.
  • 비용: t4g.medium 약 $30 + 초과 크레딧(unlimited) 추정 $18. 멘토님이 말씀하신 월 10~12만 원과 차이가 있어 이번 달 청구서로 확인하겠습니다.

5다음 단계 · EC2 3대 분리

스펙 021. 지금 EC2 한 대를 역할별 세 대로 나눕니다. 같은 VPC·서브넷 안에서 사설 IP로 통신하고, 인터넷에 열린 것은 serve 박스의 80번뿐입니다. 스펙과 런북은 작성했고 코드 변경·이전은 이번 주 안에 합니다.

바꾸는 방법

  • compose profile 세 개(collect·data·serve). depends_on은 제거.
  • 루트 .env의 DATA_HOST·COLLECT_HOST로 사설 IP 주입. nginx 업스트림은 템플릿 치환.
  • 배포는 세 타깃을 data → collect → serve 순서로 SSH.
  • 이전 절차 11단계를 런북 ec2-split.md에 적었습니다. 보안그룹 → 인스턴스 → 스왑 → env → 업비트 IP 등록 → 볼륨 tar 복사 → 순차 기동 → 탄력 IP 이동 → GitHub Secrets → 구 박스 3일 보관 후 종료.
  • 예상 중단 5분 안팎.

알고 있는 리스크

  • Redis에 인증이 없습니다. 보안그룹으로만 막습니다.
  • collect가 1vCPU라 이미지 빌드 중 수집이 3~5분 느려집니다. 빌드를 다른 데서 하는 것이 후속 과제입니다.
  • 인스턴스 재생성으로 사설 IP가 바뀌면 .env를 손으로 고쳐야 합니다.
  • 자동 롤백이 없습니다. 실패하면 구 박스로 탄력 IP를 되돌립니다(그래서 3일 보관).

7토요일에 여쭤볼 것

저희끼리 결정하기 어려웠거나, 멘토님 경험이 필요한 것들입니다.

  1. 3대 분리가 지금 규모에 맞는 크기인가요, 아니면 과한가요?
    멘토링 때는 "수집 t4g.medium + 조회 t4g.small" 2대($76)를 생각했는데, 버스터블 실측 뒤 "c7g.medium + t4g.small + t4g.micro" 3대($63)로 바꿨습니다. 수집기만 고정 성능으로 가고 나머지는 버스터블이라는 판단이 맞는지 봐주시면 좋겠습니다.
  2. DB를 별도 EC2에 두는 것과 관리형 서비스 중 어느 쪽이 나은가요?
    Redis는 ElastiCache, Influx는 Timestream for InfluxDB가 있는데 서울 리전 가능 여부와 가격을 못 봤습니다. 지금 단계에서 관리형이 비용 대비 의미가 있을지요.
  3. Redis를 계속 두는 게 맞나요?
    스프레드 표 푸시가 Redis 채널 하나로만 갑니다(폴링 fallback 삭제). 단일 경로가 된 만큼 Redis가 죽으면 표가 멈춥니다. 이대로 가도 되는지, 아니면 fallback을 다시 넣어야 하는지요.
  4. 수집기 1코어 한계를 언제 풀어야 하나요?
    거래소를 더 늘리면 프로세스 분리가 불가피합니다. 런칭 전에 해야 할지, 런칭 후 데이터를 보고 할지 판단이 필요합니다.
  5. VPC·보안 구성에서 빠진 게 있을까요?
    지금 계획은 같은 퍼블릭 서브넷에 3대를 두고 보안그룹으로만 막습니다. 프라이빗 서브넷과 NAT를 지금 넣어야 하는지, 멘토님이 준비하신 VPC 자료와 맞춰 보고 싶습니다. AWS 메타데이터 탐색 시도가 로그에 있어서 IMDSv2 설정도 같이 여쭙겠습니다.
  6. 초과 크레딧 청구액
    저희 계산은 월 $18인데 멘토님은 10~12만 원으로 보셨습니다. 이번 달 청구서를 가져가서 같이 보겠습니다.
