# MarketLens 인프라 재구성 제안

상태: DRAFT v3 (합의 대기) | 2026-09-14 | 합의된 결과는 `architecture.md` §배포 토폴로지에 반영, 코드 변경은 스펙 016~

목표: **서버 하나가 죽어도 수집은 이어지고 조회는 응답한다. 사용자가 몰리면 API 서버를 늘려서 받는다.**

## 1. 구성

```
인터넷 → [LB] → [API ×2+]  ──읽기──▶ [DB (InfluxDB)] ◀──쓰기── [파싱 ×2]
                    │                                              │
                    └──────── 최신 틱 읽기 ── [Redis] ◀── 최신 틱·리더 락 ┘
                                                                    └──▶ [S3 raw]
```

| 서버 | 대수 | 역할 |
|---|---|---|
| API | 2 이상 + LB | 조회 응답. 상태 없음 |
| 파싱 | 2 | 거래소 WS 수집, 틱 생성, DB·S3 쓰기 |
| DB | 1 | InfluxDB. 봉·틱·사건 |
| S3 | 1 | 원문 아카이브 |
| Redis | 1 (Multi-AZ) | 최신 틱 + 파싱 리더 락. **§4 참고** |

## 2. 서버별 결정

### API — 2대 + LB, 늘어날 수 있게
- ALB 뒤에 ASG(min 2, max 는 성능 테스트 후). 두 AZ 에 한 대씩.
- 상태를 프로세스 밖으로 빼야 2대가 된다. 지금은 `LiveStore` 인메모리라 워커 1개 강제 (`architecture.md:13`). → **코드 변경: 최신 틱·스트림 상태·spark 를 Redis 에서 읽기** (멘토 "실시간 = Redis 직접").
- 인스턴스: c7g.large (2vCPU 4GB, ARM). WebSocket 푸시 후 API 부하는 미미. T계열 금지 (멘토).
- **실시간 전달: 폴링 → WebSocket 푸시 + 변경분만.** 아래 §2.5.

### 파싱 — 1대 → 2대
두 대 다 거래소에 붙어 있고, **한 대만 쓴다** (핫 스탠바이).
- 리더 락: Redis `SET collector:leader <id> NX PX 5000`, 매초 갱신. 리더가 죽으면 5초 안에 다른 쪽이 잡고 쓰기 시작.
- 스탠바이는 WS 를 이미 물고 있어 이어받는 첫 틱부터 완전하다.
- 쓰기 경로(틱 relay·writer 3개·S3 업로드) 앞에 "내가 리더인가" 한 줄. → **코드 변경 1건**.
- 왜 "둘 다 쓰기"가 아닌가: 틱·봉은 Influx 덮어쓰기라 괜찮지만 `premium_event`·`collect_fail` 은 시작 시각이 키라 ±1초 차이로 중복. dedupe 새로 짜는 것보다 락 한 줄이 싸다.
- 파싱 앞에 LB 는 불필요 (멘토). 각자 EIP → 업비트 IP 허용목록에 2개 등록, 거래소 rate limit 도 IP 별 독립.
- 인스턴스: c7g.large ×2 (2vCPU 4GB, ARM). 실측(2026-09-14, t4g.medium 에서 `docker stats`): server 컨테이너가 파싱+API 합쳐 **1코어의 50~76%, 메모리 390MB** 상시. 1vCPU(c7g.medium) 는 여유가 없고, 버스터블은 이 사용률에서 크레딧이 마르므로(현재 Unlimited 로 버팀) 2vCPU 비버스터블 최소가 c7g.large. 현재 호스트가 t4g(ARM) 라 이미지는 이미 arm64.

### DB — 1대
- InfluxDB 2.7 OSS 는 복제 불가. 1대 + EBS + 일 스냅샷.
- 죽으면 조회만 멈춤. 수집은 Redis 스트림이 24h 버퍼 (`db.md:23`) → 복구 후 flusher 가 밀어 넣음. 수집 손실 없음.
- 인스턴스: r7g.large (2vCPU 16GB, ARM). 실측 Influx 상주 메모리 606MB, CPU ~0%. OOM 은 상한 없는 전 구간 조회 탓 (`status.md:31`) → **조회 창 상한**이 본질이고 메모리는 여유분. 상한 걸고도 재시작 나면 r7g.xlarge(32GB, $189).
- 관리형 대안: Amazon Timestream for InfluxDB (2.7 호환, Multi-AZ). 서울 리전·가격 미검증 → 확인 후 결정.

### S3 — 1개
- 현행 유지. lifecycle 미설정만 정리 (`db.md:30`).

### Redis — 1클러스터
- ElastiCache Multi-AZ, cache.t4g.medium. 데이터 260MB.
- 용도 3개: 틱 버퍼(현행), API 가 읽는 최신 상태(신규), 파싱 리더 락(신규).

### 2.5 실시간 전달 — 폴링을 WebSocket 푸시로

실측 (2026-09-14, 헤드리스 브라우저 20초, 클라이언트 1개):

| | theddari | 우리 |
|---|---|---|
| 방식 | WebSocket, 바뀐 코인만 ~0.6KB 프레임 | HTTP 폴링 1초, 488행 전체 (244KB, gzip 54KB) |
| 접속자 1명당 서버 송출 | ~18KB/s | ~54KB/s |
| 서버 CPU | 프레임 1회 생성 → 전원에 같은 바이트 | 접속자 수 × (요청 파싱 + 직렬화 + gzip) 매초 |
| 바이낸스 시세 | 브라우저가 직접 구독 | 서버 경유 |

theddari 는 현재가 비율 김프를 브라우저가 계산한다. 우리는 호가를 걷어 슬리피지를 뺀 값이라 브라우저로 못 옮긴다 — 488종목 호가 3거래소를 브라우저가 받으면 **1명당 2.7MB/s** (업비트 orderbook 1,315 + 바이낸스 depth20 379 + 빗썸 추정, 실측 환산). 폰에서 불가.

결정:
- **전 종목 × 매초 = 서버.** 파싱기 틱을 API 서버가 WebSocket 으로 접속자에게 브로드캐스트. 직전 틱과 달라진 행만 보낸다.
  - 소켓만으로 서버 CPU 가 접속자 비례 → 상수 (직렬화 1회). 변경분으로 트래픽 54KB/s → 수 KB/s. 멘토 지적(매초 56KB, 499, 백그라운드 폴링) 전부 해소.
  - ALB 유휴 타임아웃 기본 60초 → 서버 ping 또는 타임아웃 상향.
- **한 종목 × 지금 = 브라우저 직접.** 호가창 상세는 코인 클릭 시 브라우저가 거래소 WS 에 그 심볼만 구독 (업비트·빗썸·바이낸스 셋 다 브라우저 연결 허용 확인). 서버 비용 0. 표의 슬리피지값과 1초 안팎 어긋날 수 있어 시각 병기.
- 티커 김프를 브라우저가 계산하는 theddari 방식은 접속자 수천 명 되면 재검토. 지금은 계산 로직 TS/Python 이중화 비용이 더 크다.

## 3. 문제상황 → 해결

| 문제 | 해결 인프라 | 남는 공백 |

| 사용자 몰림 | WebSocket 푸시 + 변경분 (§2.5) 로 접속자 비례 CPU 제거, 그래도 부족하면 ASG 스케일아웃 | 스케일아웃 2~3분 |
| DB 죽음 | Redis 24h 버퍼, 스냅샷 복원 | 조회만 10~30분 |
| DB OOM (실제 발생) | 32GB + 조회 창 상한 | — |
| 디스크 풀 (09-12 실제) | 로그 로테이트 + CloudWatch 디스크 80% 알람 | — |
| CPU 100% (09-12 실제) | 파싱·DB 를 다른 박스로, T계열 → M | — |
| 죽었는데 모름 | CloudWatch 알람 → SNS, 파싱 하트비트 30초, Sentry 무료 | — |
| 봇 스캔 (로그에서 확인) | 없는 경로 404, nginx rate limit, SSH 대신 SSM | — |
| Redis 죽음 | Multi-AZ 자동 페일오버 ~1분, 파싱기는 그동안 로컬 버퍼 | 1분 |

## 4. 미결: Redis 를 뺄 것인가

진중 의견: 오버엔지니어링이라 제거.
반론: Redis 는 추가가 아니라 **현행** (`docker-compose.yml`, 파싱 → Redis 스트림 → flusher → Influx). 빼면 아래 세 가지를 대신 풀어야 한다.

| 빠지는 것 | 대안 | 대가 |
|---|---|---|
| API 가 읽을 최신 틱 | API 가 매초 Influx `range -5s` 조회 | 클라이언트 수 × 초당 1쿼리가 Influx 로. Influx 가 이미 약한 고리 |
| DB 다운 시 24h 버퍼 | 파싱기 로컬 디스크 버퍼 신규 작성 | 코드 추가, 파싱기 죽으면 버퍼도 같이 죽음 |
| 파싱 리더 락 | 둘 다 쓰기 + 사건 dedupe / 또는 수동 스탠바이 | dedupe 코드 / 또는 공백 = 사람 반응 시간 |

→ 추천: 유지. 뺄 때 줄어드는 건 노드 1개(월 ~$100), 늘어나는 건 코드 3곳.
