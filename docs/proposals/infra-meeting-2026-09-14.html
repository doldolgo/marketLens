1현재 구조

EC2 한 대(t4g.medium, 2vCPU 4GB, ARM) 위에 컨테이너 다섯 개. 인터넷에 열린 포트는 web 컨테이너의 80번 하나. 스프레드 탭은 api 컨테이너만 보고(018), 수집기는 거래소 4곳에 붙어 있습니다(019).

컨테이너하는 일상태를 가지나
webVite 빌드 정적 파일 + nginx 프록시. 경로로 server / api 분기없음
server업비트·빗썸·바이낸스·바이빗 WebSocket 수집, 1초 틱, 김프·슬리피지 계산, 표를 Redis 에 게시, Influx·S3 쓰기. 남은 HTTP 는 /health /health/collect /history/events /refresh메모리(LiveStore) — 워커 1개 강제
api같은 이미지, ROLE=api. Influx 조회 4경로 + /ws/spreads 브로드캐스트 + GET /spreads(Redis 키 그대로 반환, 018)없음 (Redis 구독·키 읽기만)
influxdb1분봉 사슬 롤업, 김프 사건, 수집 실패 구간디스크 (EBS)
redis틱 24h 버퍼(60초마다 Influx 로 flush), spreads 채널·spreads:latest(TTL 10초)·spreads:want(TTL 15초)메모리

배포 파이프라인

  • PR CI (ci.yml): server ruff·pytest, web lint·build. 문서만 바뀐 PR 도 전부 돕니다.
  • main push (deploy.yml): EC2 에 SSH → docker compose up -d --build. 배포 가드가 EC2 .env 의 INFLUX_TOKEN·S3_BUCKET 존재만 확인.
  • 워크플로 성공 = "EC2 에서 명령이 끝났다"는 뜻. 외부 URL 확인·자동 롤백은 없습니다.

수집기가 1코어를 다 씁니다. 수집 프로세스는 asyncio 단일 워커라 코어를 하나만 쓰는데, 바이빗 추가 뒤 그 코어가 85~100% 입니다. 이 상태면 거래소 메시지 처리가 밀리고 틱이 늦어질 수 있습니다(아직 경고 로그는 0건). t4g.medium 은 버스터블(기준 20%)이라 크레딧이 마르고 Unlimited 초과 과금으로 버티는 중입니다. 6장 안건 4.

6오늘 결정할 것

"제안" 은 진중 의견입니다. 합의된 결과는 architecture.md 배포 토폴로지에 반영하고, 코드 변경은 스펙 018 부터 씁니다.

  1. Redis 를 유지할 것인가, 뺄 것인가
    빼면 대신 풀어야 하는 것 3개: API 가 읽을 최신 틱(→ 매초 Influx 조회, Influx 가 이미 약한 고리) · DB 다운 시 24h 버퍼(→ 파싱기 로컬 디스크 버퍼 신규) · 파싱 리더 락(→ dedupe 코드 또는 수동 스탠바이). 줄어드는 건 월 ~$50~100.
    제안: 유지. Redis 는 추가가 아니라 현행이고, 017 이 이미 채널로 쓰고 있음.
  2. 인스턴스 — 10명 이내 기준 박스 2대(수집 t4g.medium · 조회 t4g.small)로 갈 것인가
    5장 계산: 월 약 $76, 지금보다 +$28. 조회 박스에 api·web·Influx, 수집 박스에 수집기·Redis. HA 제안($480)은 사용자가 늘 때로 미룸.
    제안: 2대. 코드 변경 없이 compose 를 둘로 나누고 Redis 포트를 사설망 보안그룹으로만 여는 인프라 작업. 020 이 끝나면 조회 박스는 그대로 API 2대의 첫 번째가 됨.
  3. 코드 변경 순서 — 020 나머지 HTTP 이동 → 021 리더 락 → 022 조회 상한 → 023 알람
    장애 빈도로 보면 022(OOM·14.8초)와 023(무알람)이 급하고, HA 로 보면 020·021 이 선행.
    제안: 022 → 023 → 020 → 021. 지금 한 대인 동안 실제로 아픈 것부터. 단 안건 4 의 CPU 대응이 이 순서보다 앞입니다.
  4. 수집기 1코어 100% — 무엇부터 할 것인가
    바이빗 추가 뒤 85~100%. 단일 워커라 인스턴스를 키워도 코어 하나만 씁니다. 선택지: (a) 먼저 프로파일 — 바이빗 orderbook.200 정렬이 원인이면 구독 깊이를 50 으로 낮춤(호가 걷기는 최대 20단계만 씀) (b) 수집기를 국내/해외 두 프로세스로 나눔 — 틱 루프가 두 메모리를 봐야 해서 큰 변경 (c) c7g 로 코어 속도만 올림 — 효과 미측정.
    제안: (a) 를 이번 주 안에. 측정 없이 (b)·(c) 로 가지 않는다. 그동안 EC2 .env 에 바이빗 키를 넣어 경고를 없앤다.
