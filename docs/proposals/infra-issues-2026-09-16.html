6멘토님이 짚지 않았지만 조사 중 드러난 문제 7개

6-1. compose에 메모리·CPU 제한이 하나도 없다

docker-compose.yml 5개 서비스 어디에도 mem_limit·cpus·healthcheck 없음. 09-15 c7g.medium 실험이 12분 만에 죽은 원인이 Influx 메모리(상주 524MB, 전 구간 조회 시 2.4GB까지)였는데, 스펙 021도 Influx 쿼리 상한 env만 걸고 컨테이너 단위 메모리 상한은 없습니다. data 박스(t4g.small 2GB)에서 Influx가 다시 폭주하면 Redis까지 같이 죽고 스프레드 표 전체가 멈춥니다(018에서 폴링 fallback 삭제).

6-2. Redis 인증 없음 + 021에서 6379·8086을 호스트에 공개

지금은 compose 내부 네트워크만이라 문제 없지만, 021은 박스 간 통신을 위해 Redis 6379·Influx 8086을 호스트 포트로 열고 보안그룹으로만 막습니다. 3대 모두 같은 퍼블릭 서브넷. 보안그룹 규칙 실수 한 번이면 인증 없는 Redis가 인터넷에 노출됩니다. 021 스펙도 "Redis 인증 없음"을 빚으로 적어 두었습니다. 멘토님이 물을 VPC 질문(프라이빗 서브넷·NAT)과 직결.

6-3. 비트겟 마켓 목록을 매초 828KB 받는다

비트겟 symbols REST 응답이 828KB인데 마켓 우주 갱신 루프가 매초 호출. 하루 약 70GB 수신. AWS 인바운드는 무료지만 매초 828KB JSON 파싱이 수집기 1코어를 갉아먹습니다. 09-07 바이낸스 exchangeInfo 17.5MB를 2.5MB로 줄인 것(커밋 3b27fc4, 매초 505ms → 88ms)과 같은 종류의 문제. ETag 조건부 요청 또는 주기 연장 필요.

6-4. 수집기가 최적화 3건 뒤에도 1코어 93%

uvicorn 워커 1개 + asyncio 루프 하나라 vCPU를 늘려도 소용없음. 거래소가 5곳(샤드 11개)이라 앞으로 거래소를 더 붙이면 다시 100%. 국내/해외 프로세스 분리가 근본 해결이지만 틱 루프가 두 메모리를 봐야 해서 큰 변경. 021의 c7g.medium 이동은 코어 속도(Graviton2 → 3) 효과인데 차이는 미측정.

6-5. 배포 후 확인과 자동 롤백이 없다

deploy.yml 성공 = SSH 명령이 exit 0으로 끝났다는 뜻. 컨테이너가 떴는지, /api/health가 200인지 안 봅니다. 021로 3타깃이 되면 한 박스 실패 시 뒤 박스는 돌지 않고 사람이 들어가 git reset 해야 합니다. 멘토님이 말한 "런칭 전 코드 프리징·테스트"(13:51)와 맞물려, 런칭 뒤에는 배포마다 사람이 브라우저를 열어 확인해야 하는 구조.

6-6. 021 배포 중 수집이 3~5분 느려진다

collect 박스가 1vCPU라 docker compose up --build 동안 이미지 빌드가 수집기와 코어를 나눠 씁니다. 표 1~2분 지연·틱 판정 stale 가능. 스펙이 "감수한다"고 적었지만 매 배포마다 데이터 품질이 흔들리는 것. CI에서 이미지를 빌드해 받아오거나(레지스트리) 빌드 전용 박스가 필요.

6-7. 프로파일 측정 원본이 레포에 없다

py-spy 비율(47%·22%)과 "틱 1초 초과 경고 291회 → 0회"는 커밋 본문·보고 자료에 결과 숫자만 있고, 측정 명령·프로파일 출력·측정 시각·접속자 수 조건이 남아 있지 않습니다. 다음에 CPU가 다시 오르면 같은 조건으로 비교할 기준이 없습니다. 멘토님이 강조한 "누가 CPU를 쓰는지 알아야 한다"를 재현 가능하게 하려면 측정 절차를 런북으로.

8우선순위 제안

"실제로 겪었거나 로그에 찍힌 것"을 먼저, "언젠가 필요한 것"을 뒤로. 판단은 팀이.

  1. nginx 404 + limit_req
    nginx.conf 두 블록 추가로 끝나는 작은 변경. 봇 스캔은 로그에 이미 찍혀 있고(13초 760회, .env 탐색), 멘토님이 두 번 반복한 지적. 021보다 먼저 해도 충돌 없음.
  2. IMDSv2 강제 확인
    서버에서 aws ec2 describe-instances로 HttpTokens 값 확인. optional이면 required로. 명령 한 줄이고 컨테이너 S3 업로드가 IMDSv2로 동작하는지만 확인하면 됨. 런북 두 곳의 명령도 같이 고침.
  3. CloudWatch 알람 3개 + SNS
    디스크 80%·CPU 90% 5분·인스턴스 상태 체크 실패. 디스크는 CloudWatch Agent가 있어야 보임. 09-12 장애 두 건이 다 "죽은 걸 나중에 알았다"였음.
  4. 스펙 021 구현 + 이전
    DB 분리·수집 박스 고정 성능·조회 분리를 한 번에. 이때 compose mem_limit(6-1)과 Redis requirepass(6-2)를 같은 PR에 넣을지 결정. 문서 불일치(7장)는 이 PR의 문서 갱신에 끼워 정리.
  5. 비트겟 symbols ETag 또는 주기 연장
    수집기 93%를 낮추는 가장 싼 방법. 프로파일로 비율 먼저 측정하고, 측정 절차를 런북으로 남김(6-7).
  6. 부하 테스트 시나리오 + APM
    토요일 멘토님 스크립트와 맞추기. 시나리오는 대시보드 진입 → 스프레드 WebSocket 구독 → 기록 탭 7일 조회 → 이탈. Sentry 무료 플랜은 FastAPI 통합 한 줄.
